# Onboarding для разработчика

Этот документ нужен, чтобы новый разработчик быстро понял продукт, запустил его локально и не задел живые интеграции случайным изменением.

## 1. Что это за проект

`vin-oil-mann` - внутренняя эко-платформа автосервиса "Там где масло". Проект вырос из VIN-подбора масла и фильтров MANN в рабочий кабинет для ежедневных операций сервиса.

Основные задачи продукта:

- видеть состояние дня на главной странице: записи, отгрузки, касса, CRM, склад, финансы;
- создавать и вести отгрузки, подбирать масло и фильтры по VIN;
- вести локальный склад, приемки, списания, инвентаризации и счета поставщиков;
- контролировать CRM-дела клиентов, записи, сообщения и дедлайны;
- делать диагностику автомобиля и отправлять клиенту публичный отчет;
- считать смены, зарплату, мотивацию, штрафы и выплаты;
- связывать локальную базу с МойСклад, AQSI, Telegram, T-Bank, YCLIENTS и другими внешними сервисами.

Проект должен ощущаться как рабочее место сервиса: плотный, спокойный, быстрый для сканирования, без маркетинговой декоративности. Больше контекста по продукту и дизайну: `PRODUCT.md` и `docs/design-brief.md`.

## 2. Пользователи и доступы

В системе есть три основные роли:

- `owner` - владелец. Видит финансовые, складские, организационные и управленческие разделы. Не требует активной смены для доступа.
- `admin` - администратор. Работает с кассой, отгрузками, CRM, клиентами, записями и складскими операциями. Для операционных разделов нужна рабочая или кассовая смена.
- `master` - мастер. Работает со сменой, отгрузками, подбором, диагностикой и частью операционных сценариев. Для операционных разделов нужна активная смена.

Авторизация живет в `src/lib/auth.ts`. Пользователи задаются через `AUTH_USERS` в формате:

```env
AUTH_USERS=owner:password:Владелец:owner,master1:password:Мастер:master
```

Пароли, измененные через интерфейс, сохраняются в таблицу `AuthPassword`.

Важно: не передавайте разработчику production `.env.local` целиком. Лучше выдать отдельные dev/staging доступы с минимальными правами.

## 3. Быстрый локальный запуск

Нужно заранее поставить:

- Node.js `>=20.9.0`;
- npm;
- PostgreSQL;
- Chrome/Chromium, если надо проверять PDF-отчеты диагностики и печатные формы.

Минимальный запуск:

```bash
npm install
cp .env.local.template .env.local
npm run db:generate
npm run db:push
npx prisma db seed
npm run dev
```

После запуска открыть `http://127.0.0.1:3000`.

Если порт занят:

```bash
PORT=3001 npm run dev
```

В `.env.local.template` уже есть локальные пользователи-заглушки:

```env
AUTH_USERS=owner:change-me-now:Владелец:owner,master1:change-me-too:Мастер:master
```

Для локальной разработки смените пароли и проверьте `DATABASE_URL`.

Seed создает демо-организацию, основной склад, несколько контрагентов, товары, остатки и базовые поля отгрузки. Это самый быстрый способ получить живой интерфейс без внешних интеграций.

## 4. Минимальные переменные окружения

Для изолированного локального запуска обычно достаточно:

- `DATABASE_URL` - PostgreSQL;
- `AUTH_USERS` - локальные пользователи;
- `AUTH_SALT` и `SESSION_SECRET` - локальные секреты;
- `APP_TIMEZONE=Europe/Kaliningrad`;
- `CRON_SECRET` - секрет ручного вызова cron-роутов.

Внешние интеграции включайте только под конкретную задачу:

- `MOYSKLAD_*` - МойСклад, импорт, чтение и запись документов;
- `LOCAL_INVENTORY_READS` / `LOCAL_INVENTORY_WRITES` - переключение чтения и записи на локальное складское зеркало;
- `PARTS_CATALOGS_API_KEY` - VIN-подбор фильтров;
- `OPENAI_API_KEY`, `SERPER_API_KEY` - подбор и обогащение рекомендаций по маслам;
- `AQSI_*` - касса и чеки;
- `ROSSKO_*` - поставщик/заказ деталей;
- `YCLIENTS_*` - записи клиентов;
- `TELEGRAM_*`, `MESSENGER_*` - мессенджер и Telegram-сессия;
- `TBANK_*` - счета поставщиков и черновики платежей;
- `PUBLIC_CLIENT_ORIGINS` - CORS для публичного клиентского сайта;
- `CHROME_PATH` / `APP_ORIGIN` / `NEXT_PUBLIC_APP_ORIGIN` - PDF и публичные ссылки.

По умолчанию в шаблоне МойСклад выключен:

```env
MOYSKLAD_ENABLED=false
MOYSKLAD_READ_ENABLED=false
MOYSKLAD_WRITE_ENABLED=false
MOYSKLAD_SYNC_ENABLED=false
```

Не включайте `MOYSKLAD_WRITE_ENABLED`, T-Bank, AQSI или Telegram production-доступы без отдельного согласования с владельцем проекта.

## 5. Команды проекта

Основные команды из `package.json`:

```bash
npm run dev                 # локальная разработка на 127.0.0.1
npm run build               # prisma generate + next build
npm run start               # production start
npm run lint                # ESLint
npm run db:generate         # Prisma Client
npm run db:push             # быстро синхронизировать схему локальной БД
npm run db:migrate          # создать dev-миграцию Prisma
npm run db:deploy           # применить миграции в deploy-среде
npm run import:moysklad     # импорт из МойСклад
npm run sync:moysklad:last-days
npm run moysklad:token
npm run worker:messenger-media
```

Точечные проверки:

```bash
npm run test:lookup
npm run test:oil-search
npm run test:openai-oil
```

Перед сдачей кода минимум запустите `npm run lint` и, если изменение затрагивает сборку, `npm run build`.

## 6. Карта папок

- `src/app` - Next.js App Router: страницы и API routes.
- `src/app/api` - серверные endpoints. Большинство приватных роутов проверяют `eco_session` через `getSession`.
- `src/components` - UI-компоненты: shell, мессенджер, диагностика, отгрузки, печать, документы.
- `src/lib` - доменная логика. Здесь основная бизнес-логика по складу, CRM, МойСклад, кассе, финансам, зарплате, диагностике и мессенджеру.
- `src/data` - справочники и тексты диагностики.
- `prisma/schema.prisma` - модели БД.
- `prisma/migrations` - миграции.
- `prisma/seed.mjs` - демо-данные для локального запуска.
- `scripts` - ручные импорты, проверки интеграций и служебные сценарии.
- `docs` - планы, аудиты, отчеты по модулям и инцидентам.
- `public` и `assets` - публичные ассеты, бренд, шрифты.
- `templates` - XLS-шаблоны.
- `platform` - статичный React-прототип/дизайн-песочница. Основное приложение сейчас находится в `src/app`.

## 8. Важные доменные границы

### Отгрузки и локальный склад

Проект постепенно уходит от постоянной работы через API МойСклад к локальной БД. Складское зеркало хранит организации, склады, товары, остатки, контрагентов, отгрузки, документы, приемки, списания, счета поставщиков и движения.

Ключевые файлы:

- `src/lib/local-inventory-read.ts`
- `src/lib/local-inventory-admin.ts`
- `src/lib/local-demand-write.ts`
- `src/lib/warehouse-inventory.ts`
- `src/lib/warehouse-product-analytics.ts`
- `src/lib/moysklad.ts`

Режимы:

- `LOCAL_INVENTORY_READS=1` - чтение из локальной БД после импорта;
- `LOCAL_INVENTORY_WRITES=1` - локальная запись отгрузок и движение остатков;
- `MOYSKLAD_WRITE_ENABLED=true` - запись во внешний МойСклад. Использовать только осознанно.

### Диагностика

Новые сценарии диагностики используют namespace `/api/diagnostics/**` и локальные модели диагностической карты.

Старый namespace `/api/diagnostic/**` оставлен для legacy-данных и старых публичных ссылок. Новые UX-фичи туда не добавлять. Подробно: `src/app/api/diagnostics/README.md` и `src/app/api/diagnostic/LEGACY.md`.

Ключевые файлы:

- `src/components/diagnostic/*`
- `src/lib/diagnostic-map-service.ts`
- `src/lib/diagnostic-photos.ts`
- `src/lib/diagnostic-report-meta.ts`
- `src/lib/pdf-render.ts`

### CRM и записи

CRM хранит дела клиентов, стадии, дедлайны, события, уведомления и заявки с публичного сайта.

Ключевые файлы:

- `src/lib/crm.ts`
- `src/lib/client-case-workflow.ts`
- `src/lib/crm-deadline-notifications.ts`
- `src/lib/appointment-source.ts`
- `src/lib/yclients/record-notifications.ts`

### Мессенджер

Мессенджер подключен в общем layout через `MessengerProvider` и `MessengerWidget`. Есть поддержка Telegram user session, шаблонов, вложений, outbox, media jobs и S3-compatible storage.

Ключевые файлы:

- `src/lib/messenger/*`
- `src/components/messenger/*`
- `scripts/messenger-media-worker.mjs`

### Финансы, касса и зарплата

Финансовый блок включает кассовые смены, расходы, P&L/cashflow, счета поставщиков, T-Bank платежи, зарплату, мотивацию, бонусы и штрафы.

Ключевые файлы:

- `src/lib/cashbox.ts`
- `src/lib/finance-center.ts`
- `src/lib/local-inventory-finance.ts`
- `src/lib/payroll.ts`
- `src/lib/payroll-motivation.ts`
- `src/lib/tbank.ts`
- `src/lib/aqsi.ts`

### Публичный API и клиентский сайт

Публичные endpoints `/api/public/*` не используют `eco_session`. Они защищаются CORS по `PUBLIC_CLIENT_ORIGINS` и простым rate-limit по IP.

Основные endpoints:

- `GET /api/public/oils`
- `POST /api/public/vin-oil`
- `POST /api/public/leads`
- `GET /api/public/stats`

## 9. База данных

Prisma-модели сгруппированы вокруг таких областей:

- смены, ставки, зарплата, мотивация и выплаты;
- пользователи и пароли;
- МойСклад sync-state и аналитика;
- CRM-стадии, сделки, клиентские дела и уведомления;
- мессенджер, каналы, сообщения, вложения и медиа-задачи;
- диагностика и диагностическая карта;
- локальные организации, склады, товары, контрагенты, остатки и документы;
- отгрузки, позиции, закрывающие документы и движения склада;
- инвентаризации;
- счета поставщиков и T-Bank.

Для локальной разработки можно использовать `npm run db:push`. Для изменения схемы, которое должно жить в репозитории, создавайте миграцию через `npm run db:migrate` и коммитьте папку миграции.

## 10. Деплой и фоновые задачи

В репозитории есть настройки Railway, Vercel и Nixpacks:

- `railway.json` запускает `npm run db:deploy` перед стартом и затем `npm run start`;
- `nixpacks.toml` ставит Node 20 и Chromium, `CHROME_PATH=chromium`;
- `vercel.json` содержит cron `/api/cron/auto-close-shifts` каждый день в `00:05`;
- `src/instrumentation.ts` стартует worker клиентских уведомлений на Node runtime.

PDF-генерация зависит от доступного Chromium и корректного `APP_ORIGIN` / `NEXT_PUBLIC_APP_ORIGIN`.

## 11. Как безопасно брать первую задачу

Хорошие первые задачи:

- поправить текст, состояние пустого списка или небольшую UI-валидацию;
- добавить read-only поле или фильтр в существующий экран;
- улучшить документ в `docs`;
- добавить маленькую проверку в API без внешней записи;
- разобрать один пользовательский сценарий и описать баг с точными шагами.

Лучше не давать первой задачей:

- запись в МойСклад, T-Bank, AQSI или Telegram;
- изменение схемы БД без понимания миграций;
- переписывание навигации, авторизации или складского движения;
- перенос legacy-диагностики без отдельного плана.

## 12. Рабочие правила проекта

- Держите route handlers тонкими, бизнес-логику кладите в `src/lib`.
- Перед новым UI смотрите существующие компоненты и стили в `src/components/platform` и `src/app/globals.css`.
- Для приватных страниц используйте `requireAuthenticatedSession` или `requireActiveShiftAccess`, если раздел зависит от смены.
- Для API проверяйте роль явно, если действие управленческое или финансовое.
- Не добавляйте секреты в `NEXT_PUBLIC_*`.
- Не коммитьте `.env.local`, `.next`, `node_modules`, `*.tsbuildinfo`, `.DS_Store`, `._*`.
- Если меняете диагностику, новые сценарии ведите через `/api/diagnostics/**`.
- Если меняете склад, отдельно проверяйте остатки, резервы, движения и документы.
- Если меняете деньги, храните суммы в копейках, как в существующих моделях.
- Перед началом работы всегда смотрите текущую ветку, незакоммиченные изменения и открытые документы в `docs`.

## 13. Чеклист знакомства на 1-2 часа

1. Прочитать `README.md`, `PRODUCT.md`, этот файл и `docs/design-brief.md`.
2. Запустить проект локально с seed-данными.
3. Войти как `owner`, открыть главную, отгрузки, склад, финансы, CRM и кабинет.
4. Войти как `master`, проверить ограничение по смене.
5. Создать тестовую отгрузку только в локальной среде.
6. Посмотреть, как отгрузка отражается в складе и на главной.
7. Открыть `prisma/schema.prisma` и сопоставить модели с экранами.
8. Выбрать первую маленькую задачу без live-записей во внешние сервисы.
