# Спецификация новой диагностики

Дата: 2026-06-01.

Источник идеи: `tgm-8.zip`, файлы `platform/data.jsx`, `platform/screens/diagnostics.jsx`, `platform/screens/diag-print.jsx`.

## Принцип

Новая диагностика строится вокруг карты диагностики. Это один быстрый рабочий экран, где мастер видит все блоки и пункты сразу, выбирает статус, добавляет комментарий, рекомендацию и фото внутри строки/карточки пункта. Старый сценарий `хаб -> блок -> узел -> назад -> следующий узел` не переносится.

Старые таблицы диагностики не удаляются на этом этапе. Новая модель добавляется рядом, затем делается адаптер/миграция и fallback для старых публичных ссылок.

## Основные сущности

- Диагностическая сессия: статус заполнения, мастер, даты старта/завершения, счетчики, публичный token.
- Автомобиль: VIN, марка, модель, год, госномер, пробег, признаки применимости узлов.
- Клиент: связь с локальным контрагентом/CRM, имя, телефон, история обращений.
- Отгрузка: связь с локальной отгрузкой, из которой открыта диагностика.
- Блок диагностики: группа пунктов в карте.
- Пункт диагностики: проверяемый узел, статус, способ проверки, измерение, комментарии, рекомендации.
- Фото: файл, подпись, порядок, связь с пунктом.
- Печатный отчет: A4/PDF-вид карты для клиента или внутренней выдачи.
- Публичный отчет: отчет по ссылке `/report/[token]`, с fallback для старых token.

## Статусы

Новые статусы берут логику из `DIAG_STATUS`:

| Код | Текст | Группа | Смысл |
| --- | --- | --- | --- |
| `unchecked` | Не проверено | neutral | Пункт еще не заполнен. |
| `normal` | Норма | result | Прямой осмотр, отклонений нет. |
| `attention` | Внимание | result | Прямой осмотр, есть замечание/контроль. |
| `replace` | Замена | result | Прямой осмотр, требуется замена/ремонт. |
| `no_access` | Нет доступа | indirect | Узел не осматривался, доступа не было. |
| `by_mileage` | По пробегу | indirect | Вывод сделан по пробегу/регламенту. |
| `by_client` | Со слов клиента | indirect | Записано со слов клиента, без прямого подтверждения. |
| `skipped` | Пропущено | neutral | Пункт сознательно пропущен. |
| `not_applicable` | Не применимо | neutral | Узла нет на автомобиле или проверка не нужна. |

Для каждого пункта дополнительно хранится способ проверки:

- `inspection` - прямой осмотр;
- `client_words` - со слов клиента;
- `mileage` - по пробегу/регламенту;
- `no_access` - нет доступа;
- `skipped` - не проверялось.

Правило: `normal`, `attention`, `replace` обычно означают `inspection`; `no_access`, `by_mileage`, `by_client` одновременно отражают и статус, и основание вывода. Это важно для честного отчета: клиент должен понимать, где мастер видел узел напрямую, а где вывод косвенный.

## Блоки и 17 пунктов

Структура новой карты должна быть постоянной, но пункты могут скрываться или получать `not_applicable`, если узла нет на конкретном автомобиле.

### 1. Жидкости агрегатов

1. Моторное масло.
2. АКПП.
3. МКПП.
4. Передний редуктор.
5. Задний редуктор.
6. Раздатка.

### 2. Сервисные жидкости

1. Антифриз.
2. Тормозная жидкость.
3. ГУР / усилитель.
4. Омыватель.

### 3. Визуальная проверка

1. Тормозные колодки / диски.
2. Пыльники.
3. Видимые течи.
4. АКБ.

### 4. Опрос клиента / регламент

1. Салонный фильтр.
2. Воздушный фильтр.
3. Свечи.

## Применимость пунктов

Пункт не должен становиться обычным обязательным пунктом, если он не применим к автомобилю.

Примеры:

- АКПП и МКПП взаимоисключаются по данным VIN/подбора или выбору мастера.
- Передний/задний редуктор и раздатка зависят от привода.
- Свечи не показываются как обязательный пункт для электромобилей и дизельных сценариев, где это не применимо.
- ГУР/усилитель может быть `not_applicable`, если жидкость усилителя не обслуживается.

Допустимое поведение UI:

- скрыть пункт из обычного списка, если применимость уверенно определена;
- показать его в свернутом/secondary-виде с пометкой `Не применимо`;
- дать мастеру вручную сменить применимость на `Нет доступа`, `По пробегу` или обычный результат.

## Экран заполнения

Новый экран должен работать как `platform/screens/diagnostics.jsx`:

- все пункты доступны на одном экране;
- блоки сгруппированы;
- статусы выбираются быстрыми кнопками;
- нет постоянных переходов между отдельными экранами агрегатов;
- комментарии выбираются чипами и редактируются свободным полем;
- рекомендации выбираются чипами и редактируются свободным полем;
- фото добавляются прямо в пункте;
- подпись к фото обязательна или доступна сразу после загрузки;
- есть динамические счетчики `Норма`, `Внимание`, `Замена`, `Косвенно`, `Не проверено`;
- есть понятная сводка по диагностике и список рекомендаций;
- есть действие печати карты и действие публикации/отправки отчета.

Для каждого пункта на экране нужны:

- название;
- текущий статус;
- быстрые статусы `Норма`, `Внимание`, `Замена`;
- быстрые основания `Нет доступа`, `По пробегу`, `Со слов клиента`;
- готовые комментарии;
- готовые рекомендации;
- свободный комментарий мастера;
- фото;
- подпись к каждому фото;
- способ проверки.

## Сводка

Сводка считается по видимым и применимым пунктам:

- `Норма` = пункты с прямым нормальным осмотром.
- `Внимание` = пункты с замечаниями без срочной замены.
- `Замена` = пункты, где нужна работа/замена.
- `Косвенно` = `no_access` + `by_mileage` + `by_client`.
- `Не проверено` = применимые пункты без результата.

`not_applicable` не должен портить процент заполнения. `skipped` должен быть виден отдельно или попадать в нейтральный счетчик, чтобы было понятно, что мастер осознанно не проверял пункт.

## Отчеты

Печатный отчет и публичный отчет должны использовать одну модель данных:

- блоки и полный список проверок;
- рекомендации клиенту;
- фото с подписями;
- честную легенду статусов, включая `Нет доступа`, `По пробегу`, `Со слов клиента`;
- данные автомобиля, клиента, мастера, отгрузки и даты.

Для новых диагностик открывается новый отчет. Для старых token допустим fallback на старый отчет, если данные старой диагностики нельзя без потерь отрисовать в новом формате.

## Черновик модели данных

Минимальная новая схема может быть такой:

- `DiagnosticSession`: `id`, `shipmentId`, `clientId`, `vehicleId`, `masterId`, `status`, `startedAt`, `completedAt`, `publicToken`, счетчики.
- `DiagnosticVehicle`: VIN, brand, model, year, plate, mileage, hints/applicability.
- `DiagnosticBlockSnapshot`: `sessionId`, `code`, `title`, `sortOrder`.
- `DiagnosticItemSnapshot`: `sessionId`, `blockCode`, `code`, `title`, `sortOrder`, `applicability`.
- `DiagnosticItemResult`: `sessionId`, `itemCode`, `status`, `inspectionMethod`, `value`, `comment`, `recommendation`.
- `DiagnosticPhoto`: `sessionId`, `itemCode`, `filePath`, `caption`, `sortOrder`.

Названия таблиц/моделей можно уточнить при реализации, но важно сохранить snapshot блоков и пунктов внутри сессии. Тогда изменение каталога будущих диагностик не исказит старые отчеты.

## UI-детали из требований 6-15

Статус в UI обязательно разделяется на две группы:

- `Результат осмотра`: `Норма`, `Внимание`, `Замена`.
- `Без прямого осмотра`: `Нет доступа`, `По пробегу`, `Со слов клиента`.

Готовые формулировки берутся из каталога пунктов: `notes` для комментариев и `recs` для рекомендаций. Клиенту нельзя показывать технические коды, raw-теги, внутренние id, закупочные цены, маржу, API-ошибки и служебные комментарии.

Фото являются частью результата пункта: несколько фото на пункт, thumbnail, крупный просмотр, удаление и редактируемая подпись. Для `Внимание` и `Замена` фото желательно; если бизнес-правило сделает фото обязательным, сводка должна показывать список пунктов без фото с понятным объяснением.

Сводка доступна всегда, без порога 50%. В ней нужны: всего пунктов, норма, внимание, замена, косвенно, нет доступа, по пробегу, со слов клиента, с фото, без фото, рекомендации сейчас, рекомендации на следующий визит. Действия: `К отчёту`, `Печать`, `Скопировать ссылку`, `Завершить диагностику`.

Старый UX не используется в новых сценариях: старый hub, block screens, обязательная карточка узла, переходы туда-сюда, порог 50% для сводки, raw-теги, старый узкий публичный отчёт и старое `Отправить отчёт` вместо понятных report actions остаются только legacy.

## API

Новый сценарий должен использовать отдельный слой API. Даже если часть данных временно пишется в старые таблицы, пользовательские экраны не должны напрямую зависеть от старых route handlers.

Операции нового слоя:

- создать диагностику для отгрузки;
- получить диагностику;
- сохранить пункт диагностики;
- сохранить фото;
- удалить фото;
- завершить диагностику;
- получить публичный отчёт;
- сохранить напоминание;
- создать CRM-задачу из рекомендации;
- добавить рекомендацию в отгрузку;
- получить print/report payload.

API не должен зависеть от устаревшая складская интеграция. Все данные берутся из локальной БД.

## Миграция данных

Безопасный вариант по умолчанию: старые диагностики остаются как legacy, новые диагностики создаются в новой схеме, старые отчёты открываются через fallback.

Если позже понадобится полная миграция, старые данные можно переносить так:

- `GREEN` -> `normal`;
- `YELLOW` -> `attention`;
- `RED` -> `replace`;
- `SKIPPED` -> `skipped`;
- `tags` -> человекочитаемые labels/comments;
- `recommendation` -> recommendation нового пункта.

Старые данные не удалять без backup.

## Acceptance Criteria

1. Пользователь открывает отгрузку и нажимает `Произвести диагностику`: открывается новая карта диагностики, не старый hub.
2. На экране видны 4 блока и актуальные пункты; статусы выбираются без отдельного экрана каждого узла.
3. `По пробегу` и `Со слов клиента` отображаются в отчёте как косвенные рекомендации, не как прямой осмотр.
4. Фото с подписью видно в диагностике, публичном отчёте и печатном отчёте.
5. Печать открывает новый клиентский отчёт по референсу `diag-print.jsx`.
6. Клиент открывает `/report/[token]` и видит новый онлайн-отчёт.
7. В отчёте нет raw-кодов, внутренних id и технических данных.
8. Новая диагностика работает на локальной БД и не зависит от устаревшая складская интеграция.
9. Старые файлы диагностики не используются в новом пользовательском сценарии.
