# Карта раздела: диагностика

Дата выгрузки: 2026-06-01  
Основной сценарий: диагностика внутри отгрузки  
Входные точки: `/shipment/new`, `/shipment/[id]`  
Публичный маршрут клиента: `/report/[token]`  
Текущий основной режим: `Быстрая диагностика` — линейный чек-лист на одном экране.  
Цель документа: передать в Figma и разработку полную карту текущего сценария диагностики, все экраны, блоки, поля, API, данные и состояния.

## Источники в коде

- `src/components/diagnostic/DiagnosticModal.tsx` — основной интерфейс диагностики: хаб, блоки, карточка узла, сводка, офферы.
- `src/data/diagnostic-catalog.ts` — каталог блоков, узлов, тегов, правил измерений, пресетов рекомендаций и шаблонов офферов.
- `src/app/shipment/new/NewShipmentPageClient.tsx` — запуск диагностики из новой отгрузки.
- `src/app/shipment/[id]/page.tsx` — запуск или повторное открытие диагностики из существующей отгрузки.
- `src/app/report/[token]/page.tsx` — публичный клиентский отчет.
- `src/app/api/diagnostic/**/route.ts` — backend диагностики.
- `src/lib/diagnostic-seed-positions.ts` — первичное создание позиций диагностики.
- `src/lib/diagnostic-regenerate-offers.ts` — пересчет счетчиков и офферов.
- `src/lib/diagnostic-local_inventory-resolve.ts` — подбор локальных товаров для офферов.
- `src/lib/diagnostic-photos.ts` — хранение и удаление фото.
- `prisma/schema.prisma` — модели `Diagnostic`, `DiagnosticPosition`, `DiagnosticPhoto`, `DiagnosticOffer`.
- `prisma/migrations/20260202000000_add_diagnostic_module/migration.sql` — миграция диагностического модуля.

## Роли и входные условия

| Условие | Поведение |
|---|---|
| Пользователь не авторизован | Internal API возвращает `401` и ошибку `Необходима авторизация`. |
| Пользователь `owner` | Может работать с диагностикой без проверки смены. |
| Пользователь `admin` или `master` | Нужна открытая рабочая смена или кассовая смена. |
| Смена не открыта | Internal API возвращает `403`, `{ needShift: true }`, ошибка `Откройте смену`. |
| Диагностика создается из новой отгрузки | Если отгрузки еще нет, сначала создается локальная отгрузка через общий сценарий сохранения. |
| Диагностика создается из существующей отгрузки | Система ищет последнюю диагностику по `shipmentId`; если нет — создает новую. |
| Публичный отчет | Доступен без авторизации по `clientReportToken`. |

## Карта сценария

1. Пользователь открывает новую или существующую отгрузку.
2. Пользователь нажимает `Произвести диагностику` или `Открыть диагностику`.
3. Для новой отгрузки система при необходимости сначала создает черновик/отгрузку.
4. Система проверяет существующую диагностику через `GET /api/diagnostic/for-shipment?shipmentId=...`.
5. Если диагностики нет, система создает ее через `POST /api/diagnostic`.
6. Backend сохраняет шапку автомобиля, мастера, связь с отгрузкой и создает позиции диагностики.
7. Открывается полноэкранная модалка `Быстрая диагностика`.
8. На одном экране пользователь проверяет карточку автомобиля, прогресс, историю и все блоки чек-листа.
9. Пользователь идет сверху вниз по сгруппированному списку узлов.
10. В каждой строке пользователь сразу ставит статус `Норма`, `Внимание`, `Замена` или `Пропущено`.
11. Для узлов с измерением значение вводится inline; статус подставляется автоматически по шкале.
12. Для желтых и красных узлов inline раскрываются теги, фото, рекомендация, комментарий и измерение, если оно есть.
13. Backend сохраняет каждый узел через `PUT /api/diagnostic/[id]/position` и пересчитывает счетчики.
14. Старый экран блока и отдельная карточка узла доступны как `Подробно` / `Открыть карточку`, но не являются основным маршрутом.
15. На desktop справа видна sticky-сводка с прогрессом, счетчиками, проблемами без фото и действиями.
16. На mobile действия закреплены в нижней sticky-панели, а блоки чек-листа работают как accordion.
17. После заполнения минимум половины позиций становится доступна сводка.
18. При входе в сводку backend пересоздает офферы через `POST /api/diagnostic/[id]/rebuild-offers`.
19. Пользователь выбирает красные офферы и может добавить их в отгрузку.
20. Пользователь копирует ссылку публичного отчета или завершает диагностику.
21. Завершение блокируется, если у желтых или красных позиций нет хотя бы одного фото.
22. После завершения диагностика получает статус `COMPLETED` и `completedAt`.
23. Клиент открывает `/report/[token]`, видит только желтые и красные позиции, фото, рекомендации и чекбокс напоминания.

## Навигация внутри модалки

| Из | Действие | Куда |
|---|---|---|
| `hub` | Клик `Подробно` у блока | `block` выбранного блока. |
| `hub` | Клик `Открыть карточку` у обычной строки | `position` выбранного узла, назад возвращает на быстрый экран. Для измеряемых узлов основной сценарий остается в строке. |
| `block` | `Назад` | `hub`. |
| `block` | Клик по узлу | `position` выбранного узла, назад возвращает в блок. |
| `position` | `Назад` | `hub` или `block`, в зависимости от точки входа. |
| `hub` | `К сводке` | `summary`, перед переходом пересчитываются офферы. |
| `summary` | `К блокам` | `hub`. |
| Любой экран | `Закрыть` | Закрытие модалки. |

### Inline details строки

| Статус | Поведение |
|---|---|
| `GREEN` | Детали по умолчанию скрыты; мастер может раскрыть их chevron-кнопкой. |
| `YELLOW` | Детали раскрываются автоматически при выборе статуса; можно свернуть. |
| `RED` | Детали раскрываются автоматически при выборе статуса; можно свернуть. |
| `SKIPPED` | Детали раскрываются при выборе статуса и показывают короткое поле причины пропуска. |

### Измерения в строке

| Узел | Input | Правила статуса | Результат в UI |
|---|---|---|---|
| `brake_fluid` | `Влажность, %` | `< 2` → `GREEN`, `2..3` → `YELLOW`, `> 3` → `RED`. | Например `2.5% → Внимание`. |
| `coolant` | `Температура замерзания, °C` | `<= -35` → `GREEN`, `-35..-20` → `YELLOW`, `> -20` → `RED`. | Например `-25°C → Внимание`. |

Измерение сохраняется из строки с коротким debounce и на blur/Enter. Для измеряемых узлов основной сценарий не требует открытия отдельной карточки.

| Элемент details | Условия | Сохранение |
|---|---|---|
| Теги | `YELLOW` или `RED` | `tags`. |
| Фото | `YELLOW` или `RED` | `DiagnosticPhoto`; thumbnails в строке, multi-upload, удаление через `DELETE /api/diagnostic/[id]/photo/[photoId]`, progress загрузки, ошибка текстом. |
| Inline-оффер | `RED` | Если есть шаблон из `RED_NODE_OFFERS`, показывается блок `Рекомендуем добавить в отгрузку` с вариантом, ценой и действиями. |
| Рекомендация | `YELLOW` или `RED` | `recommendation`. |
| Комментарий | Все статусы при раскрытии | `notes`. |
| Причина пропуска | `SKIPPED` | `notes`. |
| Свернуть | Все раскрытые details | Локально скрывает details без перехода на другой экран. |

### Быстрые действия

| Действие | Поведение | Toast |
|---|---|---|
| Отметить все нормой | Все позиции становятся `GREEN`; проблемные метаданные очищаются. | `Все пункты отмечены нормой`. |
| Отметить оставшиеся нормой | Только позиции `NOT_CHECKED` становятся `GREEN`; `YELLOW`, `RED`, `SKIPPED` не меняются. | `Оставшиеся пункты отмечены нормой`. |
| Пропустить неприменимые | Vehicle-dependent позиции `NOT_CHECKED` (`atf`, `mtf`, редукторы, раздатка, `power_steering`) становятся `SKIPPED` с причиной `Неприменимо`. | `Неприменимые пункты пропущены`. |
| Следующий непроверенный | Раскрывает нужный блок, скроллит и подсвечивает следующую позицию `NOT_CHECKED`. | `Непроверенных пунктов нет`, если все заполнено. |
| Свернуть все | Сворачивает все блоки и inline details. | `Все блоки свернуты`. |
| Развернуть проблемные | Раскрывает блоки с `YELLOW/RED` и открывает details проблемных строк. | `Проблемные пункты развернуты` или `Проблемных пунктов нет`. |
| Показать только Внимание / Замена | Фильтрует чек-лист до `YELLOW/RED`. | Без toast, активный фильтр виден в чек-листе. |
| Показать только без фото | Фильтрует чек-лист до проблемных строк без фото. | Без toast, активный фильтр виден в чек-листе. |

### Live-summary и офферы

Правая панель больше не требует обязательного перехода в отдельную сводку. Она показывает live-summary: статусы, офферы к добавлению, проблемы без фото и ссылку отчёта.

| Сценарий | Поведение |
|---|---|
| `RED` позиция с шаблоном оффера | Оффер появляется в sidebar сразу по текущим данным строки. |
| `RED` строка с шаблоном оффера | Оффер также показывается inline рядом с красным узлом: название, вариант, цена, `Добавить в отгрузку`, `Добавить позже`, `Не предлагать`. |
| `RED` строка без шаблона оффера | Показывается `Рекомендация без товара` и действие `Добавить вручную`, либо мастер может оставить только текстовую рекомендацию. |
| Добавить в отгрузку | Перед добавлением вызывается `POST /api/diagnostic/[id]/rebuild-offers`, затем выбранный вариант отправляется в `POST /api/diagnostic/[id]/add-offers-to-shipment`. |
| Добавить позже | Оффер остается в live-summary как отложенный и не блокирует диагностику. |
| Не предлагать | Оффер скрывается в текущей сессии quick mode. |
| Полная сводка | Остается отдельным режимом `summary`, но не является обязательным маршрутом для базовых действий. |

## Добавление офферов в отгрузку

1. Пользователь отмечает офферы красной зоны.
2. Для каждого выбранного оффера выбирается вариант.
3. Frontend отправляет `selections: [{ offerId, variantIndex }]`.
4. Backend проверяет, что у диагностики есть `shipmentLocalInventoryId`.
5. Backend ищет локальную отгрузку по `LocalDemand.id` или `LocalDemand.local_inventoryId`.
6. Для каждого варианта используется `productId` локального товара.
7. Если отгрузка проведена (`applicable`) и есть склад, backend проверяет остаток и списывает 1 шт.
8. Backend создает `LocalDemandPosition` с `raw.source = diagnostic-offer`.
9. Backend пересчитывает `LocalDemand.sumCents`.
10. Оффер помечается `addedToShipment=true`, сохраняется `selectedVariantIndex`.

## Замечания для редизайна и доработки

- В topbar написано `Диагностика 14 пунктов`, но каталог содержит 16 узлов. Если включена фильтрация по `vehicleHints`, итоговое количество может быть меньше 16.
- Seed позиций учитывает `vehicleHints`, но список блока в UI строится по `ALL_NODES`. Из-за этого скрытые при seed узлы все равно могут появиться в интерфейсе и создаться через upsert.
- `vehicleHints` почти не передаются из текущих входных точек, поэтому по умолчанию показываются и АКПП, и МКПП, и полный привод.
- В публичном отчете теги сейчас выводятся кодами, а не labels из каталога.
- Внутренняя карточка узла умеет загружать фото, но не показывает уже загруженные фото и не дает удалить их из UI, хотя API удаления есть.
- `Отправить отчет клиенту` сейчас только копирует ссылку; реальной отправки клиенту через SMS/мессенджер нет.
- Голосовая заметка — placeholder, хранение заметок не реализовано.
- Офферы есть не для всех красных узлов: например `mtf`, `power_steering`, `washer`, `brakes_visual`, `cv_boots`, `visible_leaks`, `survey_air_filter`, `survey_sparks` не создают текущий оффер.
- `nextVisitOnly` оффер для салонного фильтра создается, но в текущей сводке не отображается отдельным списком офферов, только желтая зона показывает рекомендации.
- Внутренний endpoint фото всегда отдает `image/jpeg`, даже если файл сохранен как `png`, `webp` или `gif`; публичный endpoint MIME определяет корректно.
- `clientWantsReminder` сохраняется, но сценарий фактического напоминания через 6 месяцев в коде этого раздела не реализован.
- История отгрузок берется из `LocalDemand` по `counterpartyId`; записи нового ядра учитываются в той же модели.
