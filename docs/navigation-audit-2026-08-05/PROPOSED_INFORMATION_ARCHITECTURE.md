# PROPOSED_INFORMATION_ARCHITECTURE

## Решение

Рекомендуется **вариант A — по рабочим процессам**. Он лучше соответствует ежедневному мышлению автосервиса: «что мне сделать сейчас», а не «в какой системе хранится объект». Верхнее меню — максимум семь разделов; личное всегда находится в меню пользователя, редкое системное — в «Управлении».

## Принципы

1. **Один объект — один канонический вход.** Cross-links допустимы, дубли в глобальном меню — нет.
2. **Личное отделено от полномочий.** Профиль, безопасность, моя зарплата, мои уведомления и мой Telegram доступны через меню пользователя.
3. **Контекст виден до действия.** Филиал/«Все филиалы» остаётся в шапке; юрлицо показывается на экране, где оно влияет на документ.
4. **Ежедневное наверху, настройка в глубине.** Верхний уровень отвечает частоте, а не количеству реализованных страниц.
5. **Скрывать, а не инвалидировать без причины.** Недоступный по роли раздел скрывается; заблокированное по состоянию действие остаётся видимым с объяснением.
6. **All branches — scope чтения, а не тотальный lock.** Мутации требуют конкретного филиала; аналитика и поиск работают агрегированно.
7. **URL стабилен отдельно от label.** Переименование меню не требует немедленной смены маршрута.

## Вариант A — по рабочим процессам (рекомендуемый)

### Desktop: верхний уровень

```text
Главное
Работа
Клиенты
Склад
Финансы
ИИ-помощник    [только при capability]
Управление     [только при capability]
```

### Полное дерево

```text
1. Главное
   ├─ Моя сводка / Сводка филиала
   ├─ Все филиалы                 [контекст all + групповая роль]
   ├─ Задачи и предупреждения
   └─ Быстрые действия            [role-based, не отдельные routes]

2. Работа
   ├─ Записи
   ├─ Отгрузки
   ├─ Диагностика
   └─ Мои работы                  [механик/мастер; при наличии данных]

3. Клиенты
   ├─ Клиенты
   ├─ Дела
   ├─ Сообщения
   ├─ Автомобили
   └─ Аналитика

4. Склад
   ├─ Товары
   ├─ Приёмка
   ├─ Корректировки
   ├─ Инвентаризации
   ├─ Пополнение
   ├─ Поставщики                  [представление контрагентов]
   └─ Аналитика

5. Финансы
   ├─ Обзор
   ├─ Касса
   ├─ Счета поставщиков
   ├─ Доходы и расходы
   ├─ Рентабельность
   ├─ Зарплата команды            [manage payroll]
   ├─ Налоги и эквайринг          [БУ/владелец]
   └─ Отчёты и экспорт

6. ИИ-помощник
   └─ Рабочий чат
      └─ локальная ссылка «Как настроен» [manage AI]

7. Управление
   ├─ Компания
   │  ├─ Филиалы
   │  ├─ Сотрудники
   │  ├─ Роли и доступы
   │  └─ Юридические лица
   ├─ Текущий филиал
   │  ├─ Основное
   │  ├─ Режим работы
   │  ├─ Сотрудники и роли
   │  ├─ Склад и касса
   │  ├─ Каналы связи
   │  └─ Связанные юрлица
   ├─ Клиентские коммуникации
   │  ├─ Автосценарии
   │  ├─ Шаблоны
   │  ├─ Каналы отправки
   │  ├─ Журнал отправок
   │  └─ Переменные
   ├─ Интеграции
   │  ├─ Финансы: T‑Bank
   │  ├─ Учёт и склад: устаревшая складская интеграция
   │  ├─ Запись: YCLIENTS
   │  ├─ Каталоги и поставщики: MANN / ROSSKO / TRONK
   │  ├─ Коммуникации: рабочий Telegram
   │  └─ ИИ и автоматизация: OpenAI / правила расчёта
   └─ Служебные инструменты        [узкая capability]
      ├─ Аудит карточек товаров
      ├─ Здоровье синхронизаций
      └─ Диагностика окружения
```

«Диагностика» и «Мои работы» не должны появляться пустыми пунктами только ради будущей архитектуры. До появления самостоятельных реестров они остаются контекстными шагами отгрузки/записи.

## Меню пользователя

```text
[Имя]
[Роль · текущий филиал]

Мой профиль
Безопасность
Моя зарплата
Мои уведомления
Мой Telegram
Доступные филиалы

Выйти
```

Правила:

- клик по аватару/имени открывает «Мой профиль» за один клик; отдельный chevron раскрывает полное персональное меню;
- пункты доступны независимо от административных capabilities, если данные принадлежат самому сотруднику;
- «Доступные филиалы» показывает членства и роли, но не настройки филиалов;
- «Аналитика клиентов», интеграции и AI settings здесь запрещены;
- `/cabinet` можно временно сохранить URL, но label становится «Мой профиль» и страница не содержит системных карточек.

## Переключатель филиала

```text
Рабочий контекст
├─ Дачная 6В           [роль: администратор]
├─ Московский 244      [роль: наблюдатель]
└─ Все филиалы         [групповая роль, только чтение]

────────────────────
Настройки текущего филиала  [branches.manage]
Управление филиалами        [group branches.manage]
```

- После выбора конкретного филиала пользователь остаётся на совместимом route; если route не поддерживает scope, переходит на Главное с объяснением.
- После выбора «Все филиалы» операции становятся read-only/недоступны, но Финансы, Клиенты и Склад открывают агрегированное чтение, если role позволяет.
- Каждая мутация в all-mode предлагает выбрать филиал, а не просто показывает disabled item.

## Second-level структура перегруженных разделов

### Финансы

Вместо 14 вкладок одной линией:

```text
Обзор
├─ Финансовая сводка
├─ P&L
├─ Cashflow
├─ План / факт
└─ Точка безубыточности

Учёт
├─ Доходы и расходы
├─ Касса
├─ Закупки и поставщики
├─ Документы
└─ Проблемы учёта

Обязательства
├─ Зарплата
├─ Налоги
└─ Эквайринг

Отчёты
├─ Экспорт
└─ Настройки              [manage finance]
```

Роль выбирает default и доступные группы; ручной переключатель «Управляющий/CFO/Владелец» не должен имитировать права.

### Аналитика товаров

```text
Результаты: обзор, лидеры, маржа
Запасы: дефицит, неликвид, никогда не продавались
Планирование: ABC/XYZ, рекомендации, новый филиал
Качество и данные: карточки, поставщики/бренды, экспорт
```

## Вариант B — по функциональным областям

```text
Обзор
Операции
CRM
Склад
Финансы
Аналитика
Автоматизация
Администрирование
```

### Детализация

- **Обзор:** сводки, задачи, предупреждения.
- **Операции:** записи, отгрузки, диагностика, кассовая смена.
- **CRM:** клиенты, дела, переписка, автомобили, клиентские коммуникации.
- **Склад:** товары, документы, инвентаризации, пополнение, поставщики.
- **Финансы:** P&L, cashflow, расходы, зарплата, налоги, документы.
- **Аналитика:** клиентская, товарная, сравнение филиалов.
- **Автоматизация:** AI, интеграции, каналы, sync jobs.
- **Администрирование:** филиалы, сотрудники, роли, юрлица, системные инструменты.

### Плюсы варианта B

- очень чистое разделение операционных, аналитических и административных экранов;
- проще масштабировать отдельную команду аналитики/автоматизации;
- знакомо пользователям корпоративных систем.

### Минусы варианта B

- «Аналитика» отрывается от объектов и заставляет выбирать сначала тип анализа;
- «CRM» остаётся термином системы, а не пользовательской задачей;
- T‑Bank, Telegram и AI попадают в общий технический «Автоматизация» без владельца бизнеса;
- восемь верхних пунктов уже на границе доступного пространства текущей шапки.

## Почему выбран вариант A

| Критерий | A: процессы | B: функции |
|---|---:|---:|
| Ежедневная скорость мастера/администратора | 5/5 | 3/5 |
| Понятность новому сотруднику | 5/5 | 3/5 |
| Связь аналитики с предметом | 5/5 | 3/5 |
| Масштабирование системных настроек | 4/5 | 5/5 |
| Mobile-пригодность | 5/5 | 3/5 |
| Соответствие текущим routes | 4/5 | 4/5 |
| **Итого** | **28/30** | **21/30** |

Вариант A сохраняет узнаваемые «Склад» и «Финансы», заменяет технический «CRM» на «Клиенты» и вводит один ясно role-gated раздел «Управление». Это минимальная ментальная миграция при максимальном разведении уровней.

## Mobile IA

### Нижняя навигация

Для операционных ролей:

```text
Главное | Работа | Клиенты | Ещё
```

Для механика:

```text
Главное | Мои работы | Склад | Ещё
```

Для бухгалтера/аналитика:

```text
Главное | Финансы | Отчёты | Ещё
```

«Ещё» содержит сгруппированные разделы, профиль и при наличии права «Управление». Пункты не дублируются одновременно в bottom nav и длинном списке.

### Mobile interaction rules

- филиал — компактный sticky context вверху; смена открывает bottom sheet;
- основные кнопки имеют touch target не меньше 44×44 px;
- глобальный поиск доступен отдельной кнопкой;
- заголовок mobile-страницы показывает `Раздел / Экран`, а не только экран;
- горизонтальные вкладки длиннее пяти заменяются segmented top-level + список/селект второго уровня;
- управление секретами и интеграциями допускается на mobile только если форма адаптирована и подтверждает контекст.

## First-time и empty state

- Главное показывает role-based «С чего начать» вместо технических KPI.
- Если пользователю доступен один филиал, switcher не требует действия, но показывает роль.
- Если нет активного филиала/членства, продукт объясняет, кто может предоставить доступ.
- Если нет активной смены, блокируется конкретное создание документа, а не чтение личной зарплаты, справочников и уведомлений.
- Управляющий впервые видит setup checklist: филиал → сотрудники → юрлицо → рабочие каналы → интеграции.

## Инварианты безопасности

- меню отражает capability, но не заменяет server/API authorization;
- переключение филиала инвалидирует кэш и пересчитывает capability для нового контекста;
- group capabilities не автоматически дают право изменять branch, если политика требует отдельного членства;
- секреты интеграций никогда не показываются полностью; owner-only действие обозначается до открытия формы;
- публичные token routes остаются вне shell и не наследуют внутреннее меню.
