# ROLE_NAVIGATION_MATRIX

## Главный вывод

Целевая навигация не может надёжно строиться на `owner/admin/master`. В продукте уже есть роли группы (`group_owner`, `group_admin`, `group_analyst`) и филиала (`branch_owner`, `administrator`, `master`, `mechanic`, `accountant`, `viewer`), но shell использует их лишь частично. Нужна единая матрица capabilities; label роли не должен быть условием бизнес-действия.

## Расхождение текущей модели

| Слой | Роли сейчас | Где используется | Риск |
|---|---|---|---|
| Legacy auth | owner, admin, master | почти всё верхнее меню, CRM, AI, integrations, salary | неизвестная роль нормализуется к admin; недостаточно для бизнеса с филиалами |
| Business group | group_owner, group_admin, group_analyst | all-branches и dashboard context | не управляет большей частью nav visibility |
| Branch membership | branch_owner, administrator, master, mechanic, accountant, viewer + permissions JSON | branch context, отдельные API, dashboard variant | не формирует единое menu/action policy |
| Shift state | owner без смены; admin/master требуют смену | `requireActiveShiftAccess` и `operationalLocked` | блокирует не только мутации, но местами личное чтение/аналитику |

До унификации нельзя считать, что disabled-ссылка отражает реальное API-право, а наличие route в меню — разрешение на действие.

## Обозначения целевой матрицы

- **M** — полный manage в своём scope.
- **W** — рабочие действия/запись без администрирования.
- **R** — чтение/аналитика.
- **SELF** — только собственные данные.
- **—** — раздел скрыт.
- Scope: **G** — группа/все филиалы, **B** — назначенные филиалы, **C** — текущий филиал.

## Правила формирования меню

1. Сначала определяется `scope`: all/group или конкретный branch.
2. Затем объединяются capabilities групповой роли, членства выбранного филиала и индивидуальных grants.
3. Shell получает готовый `navigationPolicy`, а не самостоятельно сравнивает строки ролей.
4. Раздел показывается, если есть хотя бы один доступный дочерний route.
5. Недоступные по праву пункты скрываются. Недоступные из-за состояния (нет смены, выбран all scope, sync идёт) остаются видимыми только если объяснение помогает действию.
6. `SELF` capabilities вычисляются независимо от branch shift: профиль, безопасность, личная зарплата, личные уведомления и личный Telegram.
7. Любая API/server page повторно проверяет capability; меню — не security boundary.

## Ролевой default home

| Роль | Default после входа | Быстрые действия |
|---|---|---|
| Владелец группы | Все филиалы, если это последний scope; иначе сводка филиала | проблемы, сравнение, управление филиалами |
| Администратор группы | сводка выбранного филиала | записи, отгрузки, сообщения |
| Аналитик группы | все филиалы | клиенты, склад, финансы — read-only |
| Владелец филиала | сводка филиала | новая отгрузка, касса, проблемы |
| Администратор | сводка филиала/смены | записи, новая отгрузка, сообщения |
| Мастер‑приёмщик | очередь работы | запись, отгрузка, клиент |
| Механик | мои работы | открыть работу, диагностика, найти товар |
| Бухгалтер | финансовый обзор | счета, касса, зарплата |
| Наблюдатель | доступная сводка | только назначенные/разрешённые сущности |

## All-branches policy

| Тип действия | All branches | Поведение |
|---|---|---|
| агрегированная сводка/аналитика | разрешено по group capability | данные явно помечены «Все филиалы» |
| поиск клиента/товара/документа | разрешено read-only | результат показывает филиал каждой строки |
| экспорт | разрешено по capability | scope включён в имя/шапку файла |
| создание/изменение операции | запрещено без выбранного branch | CTA открывает выбор филиала, затем продолжает действие |
| изменение branch settings | только после выбора конкретного branch | switcher — обязательный шаг |
| group management | разрешено | раздел «Управление → Компания» |
| персональные данные | разрешено | не зависят от branch scope |

## Миграция ролей

1. Инвентаризировать все проверки `user.role === ...`, `canAccess*` и API gates.
2. Сопоставить legacy-роли с временными capability presets, не изменяя права в первом релизе.
3. Добавить policy endpoint/server helper с branch/group context.
4. Перевести shell на policy, затем страницы и API по одному домену.
5. Только после parity-test разрешить новым ролям полноценный доступ.
6. Запретить fallback неизвестной роли в `admin`; безопасный default — минимальный authenticated/SELF access.
