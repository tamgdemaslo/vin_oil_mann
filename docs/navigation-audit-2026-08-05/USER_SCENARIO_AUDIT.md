# USER_SCENARIO_AUDIT

## Методика

- Клик считается от стабильного shell после входа. Открытие dropdown — один клик, выбор пункта — второй.
- Клики внутри самой предметной операции (например, заполнение формы) не считаются навигационными, но стартовая кнопка «Создать» указана отдельно.
- «Невозможно» означает, что route/UI не даёт завершить задачу, даже если backend-модель или API частично существуют.
- Целевой норматив: ежедневная задача — 1–2 навигационных клика; редкая управляющая — не более 3; контекст филиала всегда виден до изменения данных.

## Сценарии

| № | Задача | Роль / уровень | Текущий путь | Сейчас | Рекомендуемый путь | Цель |
|---:|---|---|---|---|---|---:|
| 1 | Сменить пароль | любой сотрудник / PERSONAL | меню пользователя → Кабинет → блок пароля | 2 перехода, затем скролл; пароль и системные блоки на одной странице | меню пользователя → Безопасность | 2 клика |
| 2 | Изменить адрес филиала | ФВ/ГО/ГА / BRANCH | Кабинет → Филиалы → строка филиала | 2 клика, затем **невозможно**: строка не открывается | switcher филиала → Настройки текущего филиала → Основное | 2 клика до экрана |
| 3 | Настроить рабочий Telegram филиала | ФВ/ГО/ГА / BRANCH + COMMUNICATIONS | Кабинет → Мессенджеры; альтернативно Кабинет → Интеграции → Мессенджеры | 2–3 клика; термин не отличает системный канал от переписки | Управление → Каналы связи → Рабочий Telegram | 2–3 клика; выбранный филиал виден |
| 4 | Привязать личный Telegram сотрудника | сотрудник / PERSONAL | меню пользователя → Кабинет → карточка Telegram → «Настроить рабочий Telegram» | путь приводит не к личной привязке; bot link скрыт — **невозможно** | меню пользователя → Мой Telegram → Подключить | 2 клика |
| 5 | Настроить T‑Bank | ГО; просмотр ГА/БУ / INTEGRATIONS + FINANCE | Кабинет → Интеграции → блок T‑Bank | 2 клика + поиск по длинной смешанной странице; сохранение owner-only проявляется поздно | Управление → Интеграции → T‑Bank | 2–3 клика; capability показан заранее |
| 6 | Настроить устаревшая складская интеграция | ГО/ГА/ФВ по делегированию / INTEGRATIONS | Кабинет → Интеграции → один из двух блоков устаревшая складская интеграция | 2 клика + поиск; «склад» и «аналитика клиентов» выглядят как разные интеграции | Управление → Интеграции → устаревшая складская интеграция | 2–3 клика; подключения и задания внутри одной карточки |
| 7 | Добавить сотрудника | ГО/ГА/ФВ по праву / BRANCH | Кабинет → Филиалы → нужный филиал | после 2 кликов **невозможно**: нет карточки/вкладки сотрудников | Управление → Сотрудники → Добавить; либо switcher → Настройки филиала → Сотрудники | 2–3 клика + действие |
| 8 | Создать/изменить юридическое лицо | ГО/уполномоченный БУ / LEGAL | меню Кабинет → Профиль → карточка «Организации»; route не в dropdown | 3 клика и неверное название; при создании филиала реквизиты дублируются | Управление → Юридические лица | 2 клика + действие |
| 9 | Открыть аналитику клиентов | ГО/ГА/АН/ФВ/АД / ANALYTICS | меню пользователя → Аналитика клиентов или Кабинет → Аналитика клиентов | 2 клика, но два канонических входа и неверный PERSONAL-контекст | Клиенты → Аналитика | 2 клика |
| 10 | Открыть рабочую переписку | ФВ/АД/МА / COMMUNICATIONS | иконка сообщения; либо CRM → Сообщения | 1 или 2 клика; хороший быстрый вход, но owner/admin-only | иконка сообщения; либо Клиенты → Сообщения | 1 или 2 клика, role/capability-based |
| 11 | Настроить клиентские уведомления | ГО/ГА/ФВ/АД по праву / COMMUNICATIONS | Кабинет → Профиль → «Уведомления клиентам» | 3 клика; название конфликтует с личным inbox; внутри ещё и адрес/Wi‑Fi | Управление → Клиентские коммуникации | 2 клика; адрес филиала вынесен |
| 12 | Создать новый филиал | ГО/ГА / BUSINESS_GROUP | Кабинет → Филиалы → Создать филиал | 2 навигационных + 1 action; форма смешивает branch и legal | Управление → Филиалы → Новый филиал | 2 навигационных + 1 action; юрлицо выбирается связью |

## Дополнительные ежедневные сценарии

| Задача | Сейчас | Рекомендуется | Эффект |
|---|---|---|---|
| Создать отгрузку | Операции → Новая отгрузка (2) | кнопка «Новая отгрузка» на Главном/в журнале (1), Работа → Отгрузки (2) | ежедневное действие становится быстрее, меню короче |
| Найти запись клиента | CRM → Записи (2), но permission связан с кассой | Работа → Записи (2), плюс глобальный поиск | предсказуемый рабочий контекст |

## Разбор сценариев с высоким риском ошибки

### Личный и рабочий Telegram

```text
PERSONAL
Мой Telegram → уведомления сотруднику / подтверждение личности / отключение

BRANCH + COMMUNICATIONS
Рабочий Telegram → аккаунт точки / каналы / webhook / синхронизация переписки

DAILY WORK
Сообщения → чтение и ответы клиентам, без настройки подключения
```

Эти три сценария должны иметь разные названия, маршруты, владельцев прав и визуальные статусы. Ссылка из одного сценария в другой допустима только как объясняющий secondary action.

### Филиал и юридическое лицо

```text
Филиал: адрес, телефон, график, склад, касса, сотрудники, рабочие каналы.
Юрлицо: ИП/ООО, ИНН/ОГРН, банк, подписи, префиксы документов.
Связь: филиал использует одно активное юрлицо для конкретных документов/операций.
```

Форма филиала не должна создавать «теневое» юридическое лицо. Пользователь выбирает существующее юрлицо или создаёт его отдельным, явно обозначенным процессом.

## First-time user

Это **эвристический cognitive walkthrough**, а не исследование с реальными участниками. Проверка проведена от лица нового сотрудника, которому известна только его рабочая роль; наблюдаемые факты взяты из текущего shell и страниц.

| Проверка первого входа | Ожидаемый ответ пользователя | Что даёт текущий UI | Результат |
|---|---|---|---|
| Где я сейчас работаю? | название филиала и роль | филиал виден в шапке/подстроке, роль — в профиле | PASS |
| Где начать ежедневную работу? | одна очевидная role-based задача | «Главная» открывает ещё один пункт; затем семь общих разделов | PARTIAL |
| Почему действие недоступно? | причина и следующий шаг | часть пунктов disabled из-за смены/all-mode/прав, связь причины с конкретным пунктом не всегда ясна | FAIL |
| Где мои личные данные? | меню пользователя → профиль/безопасность | «Кабинет» смешан с системным, аналитикой и интеграциями | FAIL |
| Где настройки филиала? | switcher или Управление | switcher только меняет scope; поиск ведёт в «Кабинет → Филиалы» без редактирования | FAIL |
| Где прочитать сообщение и где подключить канал? | два явно разных места | «Сообщения», «Мессенджеры», Telegram и уведомления семантически пересекаются | FAIL |
| Где клиенты? | раздел «Клиенты» | есть CRM, Дела, Записи и Контрагенты | FAIL |
| Могу ли я безопасно исследовать меню? | недоступное объясняется без потери контекста | некоторые прямые routes молча возвращают на Главную/Кабинет | FAIL |

**Итог:** 1 PASS, 1 PARTIAL, 6 FAIL. Новый пользователь понимает текущий филиал, но не получает устойчивой модели «работа → клиенты → склад → деньги → управление → личное».

### Сейчас

1. Пользователь входит и видит полное меню, зависящее от legacy-роли.
2. Для `admin/master` часть работы закрыта до открытия смены.
3. Нет короткого объяснения: какой филиал выбран, какая роль назначена, какие три задачи доступны.
4. Disabled-пункты показывают границы, но редко объясняют, что нужно сделать или у кого запросить доступ.

### Целевой первый вход

1. Экран «Вы работаете в филиале … как …» с возможностью подтвердить/сменить филиал из доступных.
2. Чек-лист максимум из трёх обязательных действий: проверить профиль, подключить личный Telegram (если требуется), открыть смену (если роль операционная).
3. Три role-based быстрых действия: мастер — записи/новая отгрузка/сообщения; механик — мои работы/диагностика/складской поиск; бухгалтер — финансы/счета/зарплата; владелец — сводка/проблемы/управление.
4. Недоступные разделы скрыты; если пункт нужен для понимания процесса, он объясняет требуемое право и владельца доступа.

## Критерии успешного сценария после переработки

- 10 из 12 заданных сценариев доступны максимум за 2 навигационных клика; T‑Bank и рабочий Telegram допускают третий уровень внутри «Интеграций/Каналов».
- Ни один PERSONAL-сценарий не ведёт в BRANCH/SYSTEM-настройку без явного предупреждения.
- Перед сохранением адреса, канала, интеграции или реквизитов пользователь видит выбранный филиал/группу/юрлицо.
- Доступность действия определяется capability, а не совпадением названия legacy-роли.
- Невозможный сценарий имеет понятный путь запроса доступа, а не молчаливый redirect на Главную.
