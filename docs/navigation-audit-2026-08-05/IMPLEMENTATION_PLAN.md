# IMPLEMENTATION_PLAN

## Статус

Это аналитический план. В рамках текущего аудита не меняются компоненты меню, routes, permissions, API, схема БД, feature flags, сборка и production. Каждый этап ниже требует отдельного согласования объёма и, где применимо, миграции данных/прав.

## Целевые показатели

| Метрика | База/наблюдение | Цель после rollout |
|---|---|---|
| Успешность 12 контрольных сценариев | 3 сценария невозможно завершить; несколько имеют ложный путь | 12/12 завершаются; 10/12 ≤ 2 навигационных клика |
| Время до первой полезной задачи нового сотрудника | нет guided path | медиана < 2 минут |
| Использование старых routes | неизвестно | < 1% navigation sessions через 90 дней |
| Молчаливые redirects из-за доступа | есть redirect на `/`/`/cabinet` | 0; всегда объясняющий 403/access state |
| Ошибки неправильного branch scope | риск не измеряется | 0 подтверждённых; scope виден перед каждым save |
| Доля поисков раздела через глобальный поиск после неудачной навигации | не измеряется | снижение на 30% для настроек/клиентских задач |
| Mobile task success | плоская IA | не ниже desktop более чем на 10 п.п. |
| Menu permission/API mismatch | не измеряется | 100% route contract tests проходят |

## Подготовительная фаза 0. Registry и baseline

**Цель:** создать единый источник истины до пяти пользовательских этапов. Фаза не меняет видимую навигацию и фактические права.

### Работы

1. Завести типизированный registry для каждого route: canonical URL, label, section, data level, frequency, capability, branch-scope, mobile priority, shell mode, legacy aliases.
2. Зафиксировать `NAMING_GLOSSARY` в продуктовых labels; определить один текущий shell, старый `AppHeader` пометить на удаление после проверки импортов.
3. Добавить аналитику: nav impression/click, search-to-route, 403, redirect source/target, branch mode, role preset без PII.
4. Добавить contract tests для текущих redirects и shell-less/public routes.
5. Провести технический аудит всех `user.role`/`canAccess*` проверок и сопоставить с доменными capabilities без изменения фактических прав.

### Выход

- согласованный registry;
- baseline dashboard метрик;
- таблица parity legacy role → capability preset;
- перечень dead/hidden routes с владельцем решения.

### Gate

Не переходить к новому меню, пока registry не покрывает 100% `page.tsx` и public/shell exclusions.

## Этап 1. Новые названия и точки входа без изменения routes

**Цель:** проверить новую ментальную модель с минимальным техническим риском и не трогать URL.

### Работы

1. Утвердить labels: Главное, Работа, Клиенты, Склад, Финансы, ИИ-помощник, Управление.
2. Переименовать пользовательские входы по `NAMING_GLOSSARY`, сохранив все текущие URL.
3. Переставить ссылки: клиентскую аналитику — в Клиенты, системные карточки — в будущую группу Управление, личные — в меню пользователя.
4. Убрать дубли аналитики/AI из глобальных точек входа, не удаляя routes и компонентов.
5. Добавить понятные тексты состояний: «Выберите филиал», «Нужен доступ …», «Откройте смену для создания».
6. Собирать метрики старых и новых точек входа.

### Проверка

- новые labels однозначно соответствуют glossary;
- ни одна старая ссылка/bookmark не ломается;
- нет дублирующих глобальных входов;
- smoke-test всех 60 page routes.

### Rollout этапа 1

Feature flag на пользователя/роль; 10% внутренних пользователей → 50% → 100%. Старые labels доступны только как аварийный rollback, не как постоянная настройка.

## Этап 2. Верхнее меню, личное меню, филиал и управление компанией

**Цель:** реализовать целевой shell и закрыть критические функциональные разрывы управления филиалом/личным профилем.

### 2A. Shell

- desktop-меню варианта A;
- меню пользователя из личных пунктов;
- действия «Настройки текущего филиала» и «Управление филиалами» в switcher;
- раздел «Управление» только при наличии хотя бы одной capability;
- контекст филиала остаётся видимым до любого изменения данных.

### 2B. Персональное

- Мой профиль;
- Безопасность;
- Моя зарплата без shift lock;
- Мои уведомления;
- рабочая личная привязка/отвязка Telegram сотрудника;
- доступные филиалы и роли read-only.

### 2C. Филиал и компания

- карточка существующего филиала;
- редактирование адреса, телефона, часового пояса и режима работы;
- сотрудники/членства/роли;
- создание приглашения и отзыв доступа;
- отдельная связь филиала с юридическим лицом;
- удаление юридических полей из branch creation flow только после отдельного плана миграции данных.

### 2D. Коммуникации и интеграции

- рабочий Telegram филиала;
- клиентские автосценарии/шаблоны/каналы/журнал;
- перенос адреса, схемы проезда, Wi‑Fi и данных зоны ожидания из client notification screen в настройки филиала;
- ежедневные «Сообщения» остаются отдельным рабочим разделом.
- каталог интеграций по категориям без изменения самих подключений/секретов на первом шаге.

### Проверка

E2E для всех 12 сценариев, keyboard/screen reader/focus trap, Esc/click outside, длинные имя/филиал, 200% zoom и видимый branch scope.

### Gate по данным

Любая правка моделей Branch/LegalEntity/Membership и миграция данных выносится в отдельное решение с dry-run, backup/rollback и production approval.

## Этап 3. Перенос/объединение страниц, redirects и удаление дублей

**Цель:** закрепить канонические места и URL только после подтверждения новой структуры.

### Работы

1. При необходимости создать `/profile/*`, `/management/*`, `/clients/analytics`; стабильные operational routes не менять без пользы.
2. Настроить redirects из `ROUTE_MIGRATION_MAP` с сохранением query/fragment/bookmarks/ссылок из уведомлений.
3. Объединить supply/restock, penalties/salary, warehouse adjustments/writeoffs после функционального diff.
4. Перенести системные части из `/cabinet`, но не оставлять две редактируемые копии одних данных.
5. Удалить dead `AppHeader` и старые client components только после статического и telemetry-подтверждения.
6. Сгруппировать 14 финансовых и 12 товарно-аналитических вкладок; сохранить совместимость query `tab`.
7. Обновить onboarding, помощь, runbooks и внутренние ссылки.

### Проверка

- contract tests всех REDIRECT/MERGE;
- отсутствие 404 для старых bookmarks и ссылок из уведомлений;
- сохранение tab/filter/period state;
- сравнение старого и нового экрана до отключения старого.

### Rollback этапа 3

- redirects включаются конфигурационно;
- старые канонические компоненты не удаляются в том же релизе, где появился redirect;
- rollback shell не откатывает данные/permissions;
- изменение моделей филиала/юрлица имеет отдельный миграционный rollback.

## Этап 4. Роли, mobile navigation и onboarding

**Цель:** добиться role-aware parity UI/API, качественного mobile и понятного первого входа.

### Работы

1. Ввести policy service/helper: user + group role + branch membership + grants + state → capabilities.
2. Заменить shell comparisons `owner/admin/master` на policy; затем по доменам перевести server/API authorization.
3. Удалить unsafe fallback неизвестной роли в `admin`; default — только authenticated/SELF.
4. Разрешить aggregate read в all-branches; мутации требуют конкретного филиала.
5. Развязать Records/Cash, Branches/Organizations и другие ошибочные permissions.
6. Внедрить role-based mobile bottom nav + сгруппированное «Ещё», touch target ≥ 44 px на 320/375/768 widths.
7. Внедрить first-time flow: роль/филиал, максимум три setup-задачи и role-based быстрые действия.
8. Для 403 показывать причину и допустимое действие вместо молчаливого redirect.

### Проверка

- policy matrix tests на каждую строку `ROLE_NAVIGATION_MATRIX`;
- UI/direct URL/API parity;
- cross-branch isolation и secrets/redaction;
- mobile task success и accessibility;
- отдельный kill switch/audit trail для capability presets.

## Этап 5. Пользовательское тестирование, аналитика и корректировки

**Цель:** подтвердить результат на реальных ролях и убрать решения, которые не улучшают метрики.

### Работы

1. Провести сценарные тесты из раздела «План пользовательской валидации» ниже.
2. Сравнить время, клики, возвраты назад, ошибочные переходы, поиск и вопросы «где находится» с baseline.
3. Разобрать mobile/desktop отдельно и по ролям, не усредняя редкие admin-задачи с ежедневными.
4. Исправить labels, порядок, defaults и access explanations короткими итерациями.
5. Через 30/60/90 дней оценить старые routes; удалить дубли только после исчезновения значимого трафика.
6. Зафиксировать финальную IA и владельца route registry.

### Выход

- 12/12 сценариев завершаются;
- достигнуты целевые показатели;
- redirects и скрытые routes имеют срок/владельца;
- новое меню становится единственным поддерживаемым вариантом.

## План пользовательской валидации

### Участники

- владелец группы — 2;
- администратор/мастер‑приёмщик — 3;
- механик — 2;
- бухгалтер — 1–2;
- новый сотрудник без знакомства с системой — 2.

### Тест

Каждый выполняет релевантные задачи из `USER_SCENARIO_AUDIT`. Фиксируются успешность без подсказки, первый неверный клик, время, понимание scope и субъективная уверенность 1–5.

### Критерии выхода

- 90% задач завершаются без помощи;
- ни один участник не путает личный и рабочий Telegram;
- 100% управляющих понимают разницу филиала и юрлица;
- 100% тестов изменения данных правильно называют текущий филиал до save;
- mobile success ≥ 80% на первом раунде и ≥ 90% после итерации.

- [ ] Unknown role не получает admin preset.
