# ТЗ на дизайн: Эко-платформа автосервиса

## 1. Кратко о продукте

**Название продукта:** Эко-платформа  
**Рабочий бренд в интерфейсе:** «Там где масло.»  
**Тип продукта:** внутренняя web-платформа для автосервиса и магазина автотоваров.  
**Главная задача:** собрать в одном интерфейсе продажи, отгрузки, подбор масла/фильтров по VIN, склад, кассу, CRM, записи клиентов, зарплату и управленческую аналитику.

Платформа используется сотрудниками в течение рабочего дня. Дизайн должен быть не рекламным, а операционным: быстрым, плотным, понятным, устойчивым к большим таблицам, длинным названиям товаров, VIN, артикулам, суммам, статусам и ошибкам интеграций.

## 2. Цели дизайна

1. Сделать интерфейс визуально цельным: сейчас разделы похожи по структуре, но им нужен единый дизайн-язык.
2. Упростить ежедневные сценарии: открыть смену, создать отгрузку, подобрать масло/фильтры, добавить позиции, принять оплату, закрыть кассу.
3. Повысить читаемость таблиц и форм: много полей, цен, остатков, артикулов, поставщиков, клиентов.
4. Сделать навигацию очевидной для ролей owner/admin/master.
5. Подготовить полноценный UI-kit для дальнейшей разработки без постоянных уточнений.

## 3. Пользователи и роли

### Владелец, `owner`

Видит все разделы. Главные задачи:

- контроль денег, прибыли, кассы, зарплаты;
- управление сменами, ставками, бонусами и штрафами;
- аналитика клиентов;
- контроль склада, счетов поставщиков и пополнения;
- доступ к CRM и операциям.

### Администратор, `admin`

Рабочая роль с расширенным доступом. Главные задачи:

- записи клиентов;
- CRM;
- отгрузки;
- касса;
- складские операции;
- работа с клиентами и контрагентами.

### Мастер, `master`

Операционная роль. Главные задачи:

- начать смену;
- создать/редактировать отгрузку;
- подобрать масло и фильтры по VIN;
- заполнить данные авто;
- работать с диагностикой;
- видеть личные начисления.

### Ограничение по смене

Для admin/master рабочие разделы блокируются, пока не открыта рабочая или кассовая смена. Дизайн должен явно показывать:

- что именно заблокировано;
- почему заблокировано;
- где начать смену;
- что уже доступно без смены.

## 4. Информационная архитектура

### Верхняя навигация

Нужен единый sticky header:

- логотип/текст бренда «Там где масло.»;
- основные разделы с dropdown-меню;
- профиль пользователя: имя, роль, переход в кабинет, аналитика клиентов, выход;
- состояние смены желательно показывать компактным индикатором.

### Основные разделы

1. **Главная**
   - быстрый статус смены;
   - главные показатели за месяц;
   - быстрые действия;
   - последние смены/начисления/события.

2. **Операции**
   - все отгрузки;
   - новая отгрузка;
   - детальная страница отгрузки;
   - предчек;
   - печатные формы: заказ-наряд, наклейки под капот.

3. **Склад**
   - товары;
   - приемка;
   - списание;
   - пополнение остатков;
   - контрагенты склада;
   - прибыль по складу.

4. **Финансы**
   - счета поставщиков;
   - прибыль;
   - касса;
   - зарплата.

5. **CRM**
   - воронка продаж;
   - сделки;
   - привязка клиента, авто, суммы, ответственного и следующего контакта.

6. **Клиенты**
   - контрагенты;
   - записи клиентов.

7. **Кабинет**
   - смена пароля;
   - смены;
   - зарплата и начисления;
   - рабочие дни;
   - бонусы и штрафы;
   - автомобили;
   - аналитика;
   - аналитика клиентов.

8. **Публичный отчет диагностики**
   - страница отчета по токену для клиента;
   - должна быть отдельной, более простой и клиентской по стилю, но связанной с брендом.

## 5. Основные пользовательские сценарии

### Сценарий 1. Начало рабочего дня

1. Пользователь входит в систему.
2. Видит главную страницу и статус смены.
3. Если смена не открыта, видит заметный блок «Начать смену».
4. После открытия смены разблокируются разделы.
5. Header меняет состояние на «Смена активна».

Нужны макеты: нет смены, смена активна, загрузка, ошибка открытия смены.

### Сценарий 2. Создание отгрузки

1. Пользователь открывает «Операции → Новая отгрузка».
2. Выбирает или создает клиента/контрагента.
3. Вводит VIN.
4. Система декодирует авто и показывает марку, модель, год, двигатель.
5. Пользователь получает подбор масла и фильтров.
6. Выбирает вариант обслуживания: эконом/оптимальный/премиум.
7. Добавляет позиции вручную или из каталога.
8. Проверяет сумму, скидки, остатки, ячейки.
9. Сохраняет отгрузку.
10. Переходит к предчеку/печати/оплате.

Нужны макеты: пустая форма, найденный VIN, ошибки VIN, нет товаров, много вариантов, ручное добавление позиции, сохраненная отгрузка.

### Сценарий 3. Работа с отгрузкой

1. Пользователь открывает список отгрузок.
2. Фильтрует по дате, клиенту, телефону, номеру, статусу.
3. Открывает документ.
4. Редактирует атрибуты авто, позиции, суммы.
5. Открывает предчек.
6. Печатает заказ-наряд или наклейки.
7. При необходимости копирует или удаляет документ.

Нужны макеты: список, пустой поиск, строка таблицы, карточка документа, action bar, подтверждение удаления.

### Сценарий 4. Кассовая смена

1. Админ/владелец открывает кассу.
2. Указывает стартовый остаток наличных.
3. В течение дня добавляет изъятия и расходы.
4. Подтягивает суммы заказов из AQSI.
5. Сверяет ожидаемый и фактический остаток.
6. Закрывает кассовую смену.
7. Просматривает журнал и историю смен.

Нужны макеты: касса закрыта, касса открыта, операции по кассе, расхождение, закрытие, история, расходные ордера.

### Сценарий 5. Складские операции

1. Пользователь открывает товары.
2. Ищет товар по названию, артикулу, OEM, бренду, SAE/API/ACEA.
3. Видит остаток, доступно, резерв, закупочную/продажную цену, маржу, ячейку.
4. Создает приемку или списание.
5. Добавляет позиции через поиск.
6. После приемки создается счет поставщика.
7. В пополнении видит дефицит и предложения поставщика.

Нужны макеты: справочник товаров, фильтры, таблица, форма товара, приемка, списание, пополнение, корзина поставщика, состояния синхронизации.

### Сценарий 6. CRM и записи

1. Админ видит канбан-воронку.
2. Создает сделку.
3. Указывает клиента, телефон, авто, сумму, источник, ответственного, следующий контакт.
4. Перемещает сделку по стадиям.
5. Создает или открывает запись клиента.
6. В журнале записей смотрит календарь/таймлайн и статусы: ожидание, подтвержден, пришел, не пришел.

Нужны макеты: CRM-канбан, карточка сделки, форма сделки, журнал записей, календарь, создание/редактирование записи.

### Сценарий 7. Зарплата и управление сотрудниками

1. Владелец открывает зарплату.
2. Видит рабочие дни сотрудников.
3. Видит расчет выплат и ставок.
4. Настраивает правила сдельной части.
5. Добавляет бонусы/штрафы.
6. Сотрудник видит только свои начисления.

Нужны макеты: владелец, сотрудник, календарь рабочих дней, таблица выплат, редактор правил, бонусы/штрафы.

### Сценарий 8. Диагностика и клиентский отчет

1. Мастер открывает диагностику внутри отгрузки.
2. Проходит блоки: агрегатные жидкости, сервисные жидкости, визуальный осмотр, опрос.
3. Для каждой позиции выбирает статус: не проверено, хорошо, внимание, критично, пропущено.
4. Добавляет фото, измерения, рекомендации.
5. Формирует предложения работ/товаров.
6. Клиент открывает публичный отчет.

Нужны макеты: модальное окно диагностики, список блоков, карточка проверки, фото, итоговая сводка, публичный отчет клиента.

## 7. Компоненты и требования к ним

### Таблицы

Таблицы являются ключевым элементом продукта. Нужны:

- плотный режим для больших списков;
- закрепленная шапка, если таблица длинная;
- понятная сортировка;
- горизонтальный скролл на мобильных;
- визуальное различие чисел, денег, статусов и действий;
- компактные row actions;
- пустое состояние и ошибка загрузки.

### Формы

Формы должны поддерживать:

- длинные названия товаров и контрагентов;
- маски для телефона, денег, дат;
- подсказки по VIN, OEM, артикулам;
- inline-ошибки;
- disabled/loading состояния;
- сохранение/отмену/удаление;
- предупреждение перед опасным действием.

### Карточки показателей

KPI-карточки нужны для:

- зарплаты;
- смен;
- прибыли;
- кассы;
- склада;
- аналитики клиентов.

Карточка должна иметь: название, значение, вторичную подпись, тон статуса.

### Статусы

Единый словарь статусов:

- успех: проведено, смена активна, оплачено, хорошо;
- предупреждение: черновик, внимание, расхождение, скоро срок;
- ошибка/критично: просрочено, критично, нет остатка, не удалось загрузить;
- нейтрально: не проверено, нет данных, пропущено.

### Модальные окна

Используются для:

- выбора товара;
- диагностики;
- комментария к записи;
- создания/редактирования записи;
- подтверждения удаления;
- ошибок интеграций.

Нужны размеры для desktop/tablet/mobile.

### Печатные формы

Отдельно подготовить аккуратные макеты:

- заказ-наряд;
- предчек;
- наклейки под капот;
- публичный отчет диагностики.

Печатные формы должны быть черно-белыми или минимально цветными, хорошо читаться на бумаге, не зависеть от темной темы.

## 8. Визуальное направление

### Характер интерфейса

- Профессиональный сервисный инструмент.
- Чистый, плотный, рабочий.
- Больше похож на современную back-office систему, чем на лендинг.
- Визуальные акценты использовать для статусов и действий, а не для декора.

### Желательные ассоциации

- надежность;
- скорость;
- учет;
- техническая точность;
- порядок на складе;
- прозрачные деньги.

### Чего избегать

- маркетинговых hero-блоков;
- больших декоративных иллюстраций;
- перегруженных градиентов;
- слишком «игрушечного» вида;
- интерфейса, где все элементы одного цвета;
- огромных карточек там, где нужна таблица;
- мелкого серого текста для важных сумм и ошибок.

## 9. Цвета и типографика

Дизайнеру нужно предложить палитру, но сохранить практичность:

- нейтральная основа: белый/серый/графит;
- основной action color: теплый янтарный/желтый можно оставить как связь с текущими кнопками;
- success: зеленый;
- warning: янтарный;
- danger: красный;
- info: синий;
- склад/финансы/CRM могут иметь легкие цветовые акценты, но не превращаться в разные продукты.

Текущие шрифты в проекте: Inter, Open Sans, Roboto. Лучше выбрать один основной шрифт для интерфейса, предпочтительно Inter.

## 10. Адаптивность

Минимальные размеры для макетов:

- desktop: 1440 px;
- laptop: 1280 px;
- tablet: 768 px;
- mobile: 390 px.

На mobile важно:

- таблицы не ломаются, а получают горизонтальный скролл или карточное представление;
- header становится компактным;
- основные действия остаются доступны;
- формы не требуют точного попадания в мелкие элементы;
- длинные VIN/артикулы/названия не вылезают за контейнеры.

1. **Figma-файл с понятной структурой страниц.**
2. **UI-kit:** цвета, типографика, сетка, компоненты, состояния.
3. **Desktop-макеты ключевых экранов.**
4. **Mobile-макеты ключевых экранов.**
5. **Прототипы основных сценариев:**
   - вход → открытие смены;
   - новая отгрузка → VIN → подбор → позиции → сохранение;
   - касса → открытие → операция → закрытие;
   - склад → товар → приемка;
   - CRM → создание сделки.
6. **Спецификация компонентов:** размеры, отступы, hover/focus/disabled/error/loading.
7. **Отдельные макеты печати:** заказ-наряд, предчек, наклейки, отчет диагностики.

## 15. Критерии приемки дизайна

Дизайн можно считать готовым, если:

- по макетам можно собрать интерфейс без дополнительных догадок;
- все основные роли имеют понятные сценарии;
- есть состояния загрузки, пустых данных и ошибок;
- таблицы читаются на desktop и не ломаются на mobile;
- формы поддерживают длинные значения;
- важные действия визуально отделены от вторичных;
- опасные действия требуют подтверждения;
- статусы имеют единый язык цвета и текста;
- печатные формы готовы отдельно от экранного интерфейса;
- дизайн выглядит как рабочая система для автосервиса, а не как промо-сайт.

## 16. Вопросы к дизайнеру перед началом детализации

1. Нужен ли полный redesign существующего интерфейса или аккуратная унификация текущего стиля?
2. Нужно ли делать dark theme в первой версии или оставить только токены?
3. Какие экраны сначала доводим до high fidelity: отгрузка, касса, склад или главная?
4. Нужно ли готовить отдельный tablet-first сценарий для мастера на рабочем месте?
5. Делаем ли для публичного отчета диагностики более клиентский визуальный стиль?

## 17. Рекомендуемый порядок работы

1. Утвердить структуру навигации и роли.
2. Собрать low-fidelity wireframes для приоритетных экранов.
3. Утвердить UI-kit.
4. Сделать high-fidelity макеты приоритета 1.
5. Проверить сценарии на реальных длинных данных: VIN, артикулы, товары, суммы.
6. После этого расширять дизайн на CRM, аналитику, диагностику и печатные формы.
