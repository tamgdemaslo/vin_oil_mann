## Приёмочные сценарии после применения migration

1. В филиале A сохранить тестовую настройку каждой интеграции; в филиале B она не видна и не используется.
2. Новый филиал показывает мастер готовности из 7 шагов; реквизиты и Telegram session не копируются, интеграции разрешено пропустить.
3. AQSI: создать две кассы, назначить одну основной, открыть смену и убедиться, что изменение связанной кассы заблокировано.
4. При недоступном AQSI отгрузка получает persistent `retry`; повтор с тем же demand не создаёт вторую запись; cron доводит её до `succeeded`.
5. Telegram: параллельная active/pending user session в одном филиале запрещена; QR другого филиала или пользователя отклоняется; disconnect не удаляет сообщения.
6. ROSSKO: сотрудник филиала выполняет поиск/заказ по настройкам своего филиала; ИИ-ассистент использует тот же resolver.
7. Владелец бизнес-группы меняет секреты; `group_admin`, `branch_owner` или пользователь с `integrations.manage` видит статусы, проверяет соединение и меняет только несекретные настройки; администратор и мастер системные настройки не открывают.
8. API никогда не возвращает API key, API hash, session, QR token, Key1/Key2 или пароль маркировки; пустое секретное поле сохраняет прежнее значение.
9. В логах и аудите присутствуют филиал, пользователь, действие и безопасный код ошибки — без секретов.
10. `OPENAI_API_KEY` и существующие сценарии ИИ не изменены.
11. Владелец видит журнал изменений и дедуплицированные внутренние уведомления; единичный timeout не создаёт уведомление, три последовательных ошибки — создают.
12. Проверка новой кассы AQSI загружает устройства из API без фискального документа; при нескольких устройствах требуется выбор из списка.
