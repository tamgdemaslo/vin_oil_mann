# Аудит сопоставления TRONK → MANN → локальный каталог

Дата: 19 августа 2026 г.
Этап: 1 — исходная архитектура и baseline до системной оптимизации.

## Резюме

Текущую систему нельзя считать прошедшей тест на 40 автомобилях. Два прежних набора по 20 записей проверяли в основном наличие кандидатов и возможность автоматического выбора, но не содержали независимой эталонной MANN-модификации и эталонного набора фильтров. Поэтому по ним нельзя вычислить точность Top-1, Top-3, долю ложных автоматических выборов и точность фильтров.

Главная проблема не сводится к одному регулярному выражению. В цепочке одновременно присутствуют:

1. неполное извлечение полей из фактических ответов TRONK;
2. две разные подсистемы нормализации;
3. смешивание поиска кандидатов и строгой проверки в одном ранжировщике;
4. жёсткие отказы по неполным и иногда пограничным данным;
5. неполная модель отрицательных признаков;
6. некалиброванная уверенность и отсутствие отдельного статуса `AMBIGUOUS`;
7. пользовательские alias/mapping, способные закреплять единичный случай как общее правило;
8. очень низкое и неоднозначное покрытие MANN-артикулов локальными товарами;
9. отсутствие независимой разметки и production-диагностики.

После начала этого аудита алгоритм, alias-таблицы и тестовые ожидания не изменялись. В рабочем дереве уже находились незакоммиченные изменения предыдущего цикла; они перечислены отдельно и не принимаются как системное решение.

## 1. Где находится текущий pipeline

Архитектурный вывод: retrieval, parsing, scoring, confidence и сохранённые подтверждения связаны внутри одного production-пути. Чистого контракта `TRONK JSON → NormalizedVehicle → candidates → scored candidates → decision` пока нет.

## 3. Точечные хаки и механизм переобучения

Прямых условий вида `if (VIN === ...)`, `if (plate === ...)` или жёсткого VIN → MANN ID в production-резолвере не найдено.

Однако найдено четыре механизма, эквивалентных case-by-case tuning:

1. Специальные ветки по марке/модели в `canonicalBaseModel`.
2. Набор case-specific aliases, сформированный после предыдущих тестов.
3. Ручное подтверждение одновременно создаёт точную связь с MANN и глобальный alias для исходного названия модели. Один подтверждённый автомобиль способен изменить поведение всех будущих автомобилей с тем же source name.
4. Прежние аудиты содержат заранее выбранные профили автомобилей прямо в коде. Те же кейсы затем превращались в regression tests, поэтому набор переставал быть независимым.

Особенно важно: текущая незакоммиченная ветка Volkswagen Passat B6 была добавлена после наблюдения конкретного сбоя. До blind-проверки её нельзя считать доказанным общим правилом.

## 8. Как сейчас выбираются кандидаты

1. По всем допустимым формам марки читаются строки MANN, максимум 25 000.
2. Строки схлопываются по `vehicleVariantKey`; при конфликте выбирается строка, у которой есть engine code.
3. Общие и служебные строки отбрасываются.
4. Несовпадение базовой модели, поколения, engine code/family, года, объёма, топлива или body code часто приводит к hard reject.
5. Оставшиеся кандидаты сортируются по score; production возвращает Top-3.

Это не соответствует целевой двухступенчатой схеме. Broad retrieval отсутствует как самостоятельный этап: строгая проверка может уничтожить правильный вариант до ранжирования, а полный пул одной марки загружается без индекса кандидатов по модели/поколению.

## 9. Текущая score/confidence-модель

Положительные веса:

| Фактор | Баллы |
|---|---:|
| марка + базовая модель | 30 |
| поколение | 25 |
| body/chassis code | 20 |
| год | 15 |
| exact engine code | 35 |
| engine family | 25 |
| объём | 15 |
| мощность | 10 |
| топливо | 7 |
| КПП | 5 |
| привод | 5 |
| само наличие condition | 5 |

Проблемы:

- score не ограничен диапазоном 0–100;
- наличие `condition` даёт баллы даже без доказанного совпадения;
- несовпадение мощности записывается как warning, но не уменьшает score;
- несовпадение КПП/привода не является отрицательным признаком;
- совместимость sedan/wagon/van/minibus не моделируется структурно;
- missing и mismatch смешаны: отсутствие поля иногда безопасно, иногда создаёт ложную уверенность;
- score кандидата не является вероятностью и не калиброван на размеченной выборке.

`high` требует score ≥ 85, разрыв и chassis/powertrain anchor. `medium` требует score ≥ 65. Но confidence вычисляется у каждого кандидата относительно следующего, поэтому второй кандидат может получить `high`, хотя первый и второй почти равны. Это логически некорректно.

Отдельного результата `AMBIGUOUS` нет. UI показывает кандидатов, но не сообщает, какое конкретное поле нужно уточнить.

## 10. Baseline до изменений

### Что можно измерить

На прежнем hardcoded наборе из 20 профилей:

- автоматический выбор: 0/20;
- хотя бы один кандидат: 18/20;
- без кандидатов: 2/20.

На 11 уникальных декодированных автомобилях из локального cache:

- автоматический `high`: 3/11;
- требуется подтверждение: 4/11;
- без MANN-кандидата: 4/11.

Среди явных причин на cache-наборе наблюдались:

- каталог не содержит нужный двигатель/поколение;
- граничный год TRONK на год раньше начала MANN;
- chassis/body code трактуется как строгий конфликт;
- несколько кандидатов имеют одинаковый score;
- модель нормализована, но точная MANN-модификация отсутствует.

### Что измерить нельзя

Без эталонного `expectedMannVariantKey` и эталонных фильтров нельзя честно посчитать:

- Top-1 accuracy;
- Top-3 accuracy;
- false positive rate автоматического выбора;
- долю корректных `AMBIGUOUS`/`NO_MATCH`;
- точность найденных фильтров;
- долю ложных локальных товарных сопоставлений.

Поэтому приведённые выше цифры — coverage/decision baseline, а не accuracy. Называть их «40 успешно протестированных номеров» было некорректно.

## 12. Топ причин ошибок

| Приоритет | Категория | Системная причина | Наблюдаемый эффект |
|---:|---|---|---|
| 1 | EVALUATION | Нет независимой разметки A/B/C | Точечные улучшения невозможно отличить от переобучения |
| 2 | TRONK_MAPPING | Не все реальные поля извлекаются | Теряются год, топливо, кузов, engine description и часть fallback-ответов |
| 3 | MANN_DATA_GAP | PDF-каталог неполон и неструктурирован | Правильной модификации физически нет либо она выглядит как служебная строка |
| 4 | NORMALIZATION | Логика разделена и содержит model-specific branches | Одинаковые признаки интерпретируются по-разному, растёт число исключений |
| 5 | RETRIEVAL | Broad retrieval отсутствует | Правильный кандидат может быть hard-rejected до ранжирования |
| 6 | SCORING | Нет полноценного negative evidence | Мощность/КПП/привод слабо защищают от ложного выбора |
| 7 | CONFIDENCE | Gap считается локально для каждого кандидата | Некорректные `high`, нет общей калибровки и `AMBIGUOUS` |
| 8 | OVERFIT | Ручной выбор создаёт глобальный alias | Один кейс влияет на весь модельный ряд |
| 9 | LOCAL_PRODUCT | 29,1% покрытия и высокая неоднозначность | Верный MANN-артикул часто нельзя безопасно добавить в отгрузку |
| 10 | OBSERVABILITY | Production trace выключен, timing/причины не агрегируются | Реальные regressions и latency нельзя измерить |

## Оценка прежнего test harness

`scripts/audit-mann-vehicle-matching.mjs`:

- 20 профилей вшиты в код;
- make/model/year подставляются вручную вместо полного TRONK pipeline;
- нет expected MANN key;
- проверяется наличие кандидата/auto-select, не correctness.

`scripts/audit-mann-filter-local-matching.mjs`:

- ещё 20 профилей вшиты в код;
- может вызвать TRONK и пройти до локального товара;
- нет независимой разметки MANN-модификации и фильтров;
- набор уже использовался для настройки alias, поэтому больше не является blind.

Юнит-тесты полезны как regression safety, но преимущественно состоят из вручную выбранных golden cases. Property-based проверок инвариантов нет.

## Готовность исторических данных для A/B/C

В исследованном snapshot отгрузок:

- 6 110 записей;
- 4 138 записей с валидным форматом российского госномера;
- 2 400 уникальных валидных госномеров;
- 4 540 записей с моделью автомобиля.

Этого достаточно для непересекающихся A=20, B=20 и C=100 с фиксированным seed, дедупликацией по нормализованному госномеру и стратификацией по маркам/возрасту. Самые частые группы включают Toyota, BMW, Mercedes-Benz, Hyundai, Volkswagen/VW, Kia, Skoda, Nissan, Audi и Ford.

В snapshot отсутствует надёжно заполненный отдельный атрибут года; год и модификацию придётся получать из TRONK и затем независимо размечать по MANN. Историческое текстовое поле модели можно использовать только как дополнительную проверку, не как ground truth.

## План системного исправления после фиксации baseline

1. Создать воспроизводимые manifest A/B/C с seed, hash идентификаторов, запретом пересечений и неизменяемыми expected labels.
2. Написать один end-to-end harness, который сохраняет сырой TRONK JSON, normalized vehicle, retrieval pool, Top-5 с feature contributions, decision и filters/local matches.
3. Централизовать адаптеры TRONK по endpoint и единый `NormalizedVehicle`.
4. Построить отдельный структурированный индекс MANN-признаков и отчёт качества parser-а; не менять исходные строки.
5. Разделить broad retrieval и scoring. Retrieval должен сохранять 20–100 разумных кандидатов и не применять спорные hard rejects.
6. Заменить текущий score на bounded 0–100 с явными positive/negative/missing features и invariant tests.
7. Ввести единое решение `HIGH/MEDIUM/LOW/NONE` и отдельный `AMBIGUOUS`, учитывающий Top-1/Top-2 gap, completeness и конфликтующие сильные признаки.
8. Не разрешать ручному подтверждению автоматически создавать глобальный alias. Mapping и alias должны иметь разный scope, provenance и процесс валидации.
9. Разделить точность MANN-модификации, точность MANN-фильтров и качество локального product matching — это три разных метрики.
10. Заморозить алгоритм после A, затем один раз открыть B; после изменений по B запускать новую unseen C без донастройки.

## Решение по этапу 1

Переходить прямо к добавлению новых alias нельзя. Сначала нужен валидный harness и независимые labels. Иначе следующий цикл снова оптимизирует видимые номера вместо общего алгоритма.

Критерии приёмки из задания пока не достигнуты и не могут быть честно оценены на существующих данных. Первый измеримый milestone следующего этапа: manifest A/B/C, schema ground truth и baseline со значениями Top-1/Top-3/FPR/ambiguity/filter accuracy.
