# Аудит себестоимости и валовой прибыли — 1 сентября 2026

## Статус и ограничения

Аудит выполнен до любых изменений расчётной логики. Production Timeweb проверялся только чтением, внутри транзакций `READ ONLY` с ограничением времени выполнения. Исторические данные, схема БД и production-приложение не изменялись.

Вывод: текущая модель данных уже содержит необходимые денежные поля, поэтому для forward-only исправления новая колонка или миграция схемы не требуется. Отдельная data migration понадобится только для подтверждённого восстановления начальной/исторической себестоимости. Она не входит в этот этап и не должна запускаться без отдельного согласования и свежей проверенной резервной копии Timeweb.

## Правильный контракт полей

| Поле | Единственный смысл | Может меняться |
| --- | --- | --- |
| `LocalProduct.buyPriceCents` | последняя цена закупки из последнего проведённого прихода | да, новым приходом |
| `LocalStockBalance.buyPriceCents` | текущая средневзвешенная себестоимость остатка в конкретном `branchId + storeId + productId` | да, приходом/возвратом/корректировкой |
| `LocalDemandPosition.buyPriceCentsPerUnit` | неизменяемый снимок себестоимости товарной строки в момент проведения продажи | нет после проведения; при возврате в черновик сохраняется |
| `InventoryLedgerEntry.unitCostSnapshot` | цена движения на момент операции | нет |
| `InventoryLedgerEntry.totalCostSnapshot` | округлённая стоимость всего движения | нет |
| `LocalInventoryDocumentPosition.priceCentsPerUnit` | цена единицы прихода либо снимок средней цены списания | нет после проведения |

Для услуги без складского учёта себестоимость равна явному `0`, источник — `service`, статус — `confirmed`. Для товара отсутствие подтверждённой цены означает `null`, источник — `missing`, статус — `missing`; подмена нулём запрещена.

## Формулы

При приходе товара:

```text
newAverage = round((oldQuantity × oldAverage + receiptQuantity × receiptPrice)
                   / (oldQuantity + receiptQuantity))
```

Если старый остаток не положительный, новая средняя равна цене прихода. Если старый остаток положительный, но его средняя цена неизвестна, проведение прихода блокируется до задания подтверждённой opening cost: молчаливое использование цены карточки исказило бы историю.

Продажа и списание не меняют среднюю цену остатка. Их снимок берётся из текущего `LocalStockBalance.buyPriceCents` в той же транзакции, в которой меняется остаток. Денежный итог строки округляется до копейки после умножения целочисленной цены в копейках на `Decimal(14,3)` количество.

```text
revenue = round(quantity × salePrice × (1 - discount / 100))
cost    = round(quantity × costSnapshot)
profit  = revenue - cost
margin% = revenue > 0 ? profit / revenue × 100 : null
```

## Найденные причины

1. Проведённый приход увеличивает количество и обновляет цену карточки, но не рассчитывает `LocalStockBalance.buyPriceCents` и не создаёт складскую ledger-запись. Поэтому карточка стала неявным источником себестоимости.
2. При создании/изменении отгрузки снимок берётся из остатка с fallback на карточку ещё на стадии черновика. При проведении актуальная средняя не фиксируется повторно.
3. Обновление черновика предпочитает текущую цену карточки уже существующему снимку. Это меняет себестоимость при reopen/repost.
4. Списания используют цену карточки и fallback `0`, а не среднюю цену остатка. Ledger для приходов и списаний отсутствует.
5. Финансы, dashboard, аналитика клиентов, аналитика товаров и payroll используют разные fallback-правила. Часть считает отсутствующую товарную себестоимость нулевой, часть подставляет текущую цену карточки, часть исключает строку.
6. Для услуг существующий ненулевой снимок местами вычитается как себестоимость, хотя услуги без складского учёта должны иметь явный `0`.
7. `InventoryLedgerEntry.totalCostSnapshot` в проверенных движениях продаж не заполнен.

### Остатки

| Метрика | Основной филиал | Второй филиал |
| --- | ---: | ---: |
| Положительных остатков | 667 | 193 |
| Положительных остатков без средней цены | 63 | 193 |
| Положительных остатков с нулевой ценой | 6 | 0 |
| Оценка остатка по полю средней цены | ₽1 432 094,77 | ₽0,00 |
| Оценка тех же остатков по текущей цене карточки | ₽1 556 908,66 | ₽455 015,84 |

Совпадение средней с карточкой у части строк не доказывает корректность: приход никогда не рассчитывает средневзвешенное значение. У второго филиала это видно однозначно — все ненулевые остатки имеют `NULL`.

Реальный пример: `BARDAHL XTEC 5W-30 C2/C3, 1 л` поступил 2 шт. по ₽1 672 и 1 шт. по ₽1 756. Корректная средняя — ₽1 700. В остатке сохранён `NULL`, в карточке — последняя цена ₽1 756.

### Продажи и перепроведение

У `Shell HELIX ULTRA 5W-40, 4 л` были приходы по ₽5 000 и ₽4 320 и продажи между ними. Сохранённые снимки после первого прихода следовали последней цене ₽4 320. По хронологической средневзвешенной модели продажи 14 июля и 18 августа должны были получить примерно ₽4 546,67 за единицу, а продажа после следующего прихода — примерно ₽4 433,50. Это подтверждает системное использование last purchase cost вместо average cost.

В журнале редакций 14 из 20 `REPOSTED` основного филиала и 8 из 16 второго филиала изменили cost-сигнатуру непосредственно между snapshot before/after события. `REOPENED` сам снимок не меняет, но последующее обновление/повторное проведение может его заменить.

На реальном товаре `Mobil 1 ESP 5W-30, 1 л` цепочка post → reopen → repost сохранила ₽1 400, однако средняя в остатке была `NULL`; снимок совпал с текущей карточкой случайно. Ledger содержит цену движения ₽1 400, но не содержит total cost.

### Расхождение отчётов

Единый ожидаемый расчёт здесь означает: товары — только по сохранённому snapshot, услуги — cost `0`, товарные строки с неизвестной ценой не превращаются в прибыль.

| Период | Филиал | Товарных строк без cost | Текущий dashboard/customer profit | Ожидаемая известная прибыль |
| --- | --- | ---: | ---: | ---: |
| Вся история | Основной | 2 | ₽16 357 669,92 | ₽16 351 016,92 |
| Текущий месяц | Основной | 0 | ₽14 536,00 | ₽14 537,00 |
| Вся история | Второй | 2 | ₽85 108,05 | ₽78 728,05 |

Две неизвестные товарные строки основного филиала имеют выручку ₽7 327,00, второго — ₽6 380,00. Dashboard/customer analytics сейчас полностью включает эту выручку в прибыль. В основном филиале дополнительно ₽674,00 накопленной себестоимости услуг ошибочно уменьшает прибыль; в текущем месяце эффект равен ₽1,00. После исправления неизвестная прибыль должна возвращаться как `null`/incomplete, а не как число с нулевой себестоимостью.

Если удалить snapshot у продажи `Shell` и затем изменить карточку с ₽4 320 до ₽5 000, fallback-отчёт изменит историческую прибыль строки с ₽2 370 до ₽1 690. Dashboard при том же отсутствующем snapshot покажет ₽6 690 прибыли, то есть 100% выручки. При наличии неизменяемого snapshot изменение карточки на историю не влияет.

## Forward-only реализация

1. Один модуль costing отвечает за средневзвешенную цену, денежное округление, классификацию service/product, source/status и расчёт прибыли.
2. Проведение прихода под блокировкой остатка рассчитывает новую среднюю, обновляет last purchase price карточки и пишет receipt ledger с unit/total snapshots.
3. Проведение продажи/списания под той же транзакцией читает среднюю конкретного склада, записывает immutable snapshot и ledger unit/total. Неизвестная товарная цена блокирует проведение с предметной ошибкой.
4. Reopen отменяет количество по исходному snapshot, не пересчитывая его. Repost без изменения состава использует сохранённый snapshot; новая/заменённая строка получает текущую среднюю.
5. Все отчёты используют сохранённые snapshots. Никакой отчёт по проведённым документам не читает текущую цену карточки как fallback.
6. После смены snapshot/проведения/отмены инвалидируются warehouse, finance, dashboard, customer analytics и payroll.

Реализованный контур покрывает существующие операционные пути: приход, продажу, reopen/repost продажи, списание, инвентаризационный излишек/недостачу и безопасный откат прихода/инвентаризации. Модель `BranchStockTransfer` сейчас используется только в истории товара: в приложении нет сервиса проведения перемещения и нет товарных строк с количеством/ценой движения. Поэтому придумывать бухгалтерское движение поверх одной metadata-модели небезопасно. Если операционный transfer будет добавлен, обязательный контракт уже определён: source ledger списывает по средней источника, destination ledger получает тот же immutable snapshot и пересчитывает среднюю назначения. Отдельного supplier/customer return workflow в текущем коде также нет; reopen проведённой продажи является поддержанным количественным возвратом по исходному snapshot.

Добавлены две read-only CLI-проверки: `npm run audit:inventory-cost-history` для текущего состояния и `npm run rebuild:inventory-cost-history -- --dry-run` для классификации восстанавливаемых остатков (короткие алиасы `audit:inventory-costs` и `rebuild:inventory-costs:dry-run` также доступны). Обе явно отвергают `--apply`; dry-run не выполняет записей.

## Отдельный план data migration/backfill — не запускать без согласования

1. Создать и проверить свежую manual backup Timeweb непосредственно перед любыми изменениями данных.
2. Dry-run собирает хронологию по `branchId + storeId + productId`: подтверждённый opening balance/cost, приходы, продажи, списания, инвентаризации, возвраты и перемещения.
3. Для товара, у которого до первой подтверждённой цены уже есть положительный остаток/расход, пометить `opening_cost_required`; не подставлять цену карточки автоматически.
4. Владелец подтверждает opening cost и источник для каждой неоднозначной группы.
5. Отдельно согласовать, нужно ли переписывать исторические `LocalDemandPosition` snapshots. По умолчанию история продаж остаётся неизменной, а backfill заполняет только opening/current balance для безопасного forward cutover.
6. Apply-режим выполняется идемпотентно, с audit trail старого/нового значения и reconciliation до копейки и количества.
7. После применения повторить отчёт и доказать: current stock = opening + входы − выходы; отсутствуют отрицательные остатки и товарные snapshot `0/NULL` в новых проведённых документах.

## Production gate

Forward-код нельзя безопасно выкатывать как незаметное изменение, пока 256 положительных остатков без средней цены не получили подтверждённую opening cost: строгая новая логика намеренно заблокирует их продажу/приход. Допустимы два осознанных варианта: сначала отдельно согласованный data cutover либо выкладка со специально принятым бизнесом блокирующим поведением. Исторический backfill не является частью текущего разрешения.
