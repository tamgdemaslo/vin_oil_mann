# Один общий комплект на сеть — подготовленный релиз

Статус: 31.10.2026 пользователь подтвердил резервную копию, перенос четырёх
комплектов и публикацию. Подготовлены и проверены код, миграция и план переноса.
Итог применения фиксируется после проверки рабочего деплоя.

## Поведение

- Комплект создаётся один раз в `SharedProductKit` для `businessGroupId`.
  Одна строка в каталоге; один ID, название, состав, количества, версия и архив
  для всех филиалов сети. Другие бизнес-группы его не видят.
- Наличие рассчитывается отдельно по свободным остаткам каждого склада каждого
  доступного филиала. Запасы разных складов не суммируются в один комплект.
- Цена и карточки товаров принадлежат текущему филиалу. В отгрузку добавляются
  только его локальные товары. Связь с исходным филиалом создания не требуется.
- Товары сопоставляются по точной идентичности: бренд, артикул, единица учёта,
  фасовка, объём, масса, модификация. Явно выбранная карточка имеет приоритет.
  Поиск кандидатов использует сохранённые ID и исходные артикулы; форматные
  различия артикула могут потребовать ручного выбора в редакторе.
- Отсутствующая, архивная, изменившаяся или неоднозначная карточка блокирует
  доступность. Редактор позволяет выбрать ту же запчасть текущего филиала.
  Эта привязка не меняет товар в других филиалах. Изменение состава или
  количества, напротив, меняет общий комплект. Разная фасовка не конвертируется.
- Неполный расчёт не выдаётся клиенту как готовая цена; копирование предложения
  доступно после проверки местных товаров и цен.
- Общие правки разрешены владельцу и администратору сети, владельцу филиала,
  администратору и мастеру-приёмщику. Механик, наблюдатель и аналитик не получают
  права менять общий состав; читать доступные комплекты и использовать местные
  товары в разрешённой отгрузке можно без права редактирования каталога.
- Целевой запас остаётся отдельным для каждого склада. Общая версия защищает
  состав, привязки, архив и цели от потери одновременных правок.
- Создание идентичного общего комплекта блокируется сервером; параллельные
  создания сериализуются блокировкой бизнес-группы.

## Изменение базы и перенос

SQL: `prisma/migrations/20261031090000_shared_product_kits/migration.sql`.
Добавляется одна таблица `shared_product_kits` с внешним ключом на сеть,
проверками JSON, положительной версии и длины названия. В ней находятся состав,
привязки локальных товаров, цели по складам и прежние ID.

Скрипт `scripts/migrate-shared-product-kits.mjs` по умолчанию только читает данные
в read-only транзакции и пишет локальный отчёт с правами `0600`. Применение требует
точного отпечатка исходных данных и отдельного отпечатка рассмотренного плана.
Вне изолированной локальной БД также обязательны явный флаг подтверждения и
проверка свежей завершённой резервной копии именно ресурса Timeweb 4195453.
Заполненный общий каталог не перезаписывается.

Объединяются только одинаковые названия и точные составы с теми же количествами
внутри одной сети и одинакового состояния архива. Неполные идентичности и
неоднозначные карточки не склеиваются по названию. При конфликте старых целевых
запасов сохраняется максимум, а конфликт явно попадает в отчёт для рассмотрения.
Старые таблицы, карточки товаров, остатки и документы сохраняются.
Прежние ID комплектов становятся ссылками на общую запись. Начальная общая
версия превышает все версии исходных записей, чтобы старые открытые страницы
не перезаписали перенесённый состав.

Проверка рабочей базы 31.10.2026 выполнена только для чтения:
**4 исходных комплекта → 4 общих комплекта**, точных дублей и предупреждений нет.
Подробный план остаётся в приватном временном файле вне репозитория.
Отпечаток исходных записей: `7a7323871c001b7d1f69108e18b33715a6fc8ebd49da3f2d335a08a678b8f399`.
Отпечаток рассмотренного плана: `b01a5a4d2a71e7027130184cbeeaa8e5a86622f634463d33b4f84533465a7a83`.
Перед применением отпечатки перепроверяются; при изменении исходных данных
операция прерывается и нужен новый план.

## Порядок публикации после подтверждения

1. Сверить релиз с актуальным `main`, проверить отсутствие других непроверенных
   миграций, выполнить `npm run check:timeweb-only`.
2. Создать и проверить свежую резервную копию Timeweb. На время переноса
   приостановить редактирование комплектов до запуска новой версии.
3. Применить только указанный SQL отдельной транзакцией с `ON_ERROR_STOP`.
   Зарегистрировать именно эту миграцию через
   `prisma migrate resolve --applied 20261031090000_shared_product_kits`.
   Не запускать автоматическое применение всех ожидающих миграций.
4. Выполнить скрипт с `DATABASE_URL` проверенного Timeweb-ресурса,
   `SHARED_KIT_MIGRATION_APPROVED=yes`, `TIMEWEB_CLOUD_TOKEN` из защищённого
   окружения и аргументами `--apply`, `--backup-id=<verified-id>`,
   `--expected-sha256=<reviewed-source-fingerprint>`,
   `--expected-plan-sha256=<reviewed-plan-fingerprint>`,
   `--report=<new-private-local-file>`.
5. Опубликовать только подготовленные изменения через `main` и Timeweb App
   Platform. Проверить деплой, `/api/health/live`, `/api/health/ready`, создание
   общего комплекта и добавление местных товаров в отгрузку другого филиала.

До пункта 5 прежний код продолжает читать прежние таблицы. После импорта и до
смены версии редактирование комплектов должно оставаться приостановленным:
обратной синхронизации нового каталога со старым нет.

Откат приложения сохраняет добавленную таблицу и прежние таблицы. Если после
релиза уже меняли общие комплекты, их новые правки нужно сохранить и отдельно
согласовать возврат на старую модель; слепой откат потеряет видимость этих правок.
