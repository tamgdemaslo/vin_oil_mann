# Публикация моторных масел из CRM на клиентский сайт

Дата реализации: 11.09.2026.

## Что реализовано

- Товар CRM по умолчанию скрыт от клиентского сайта. Публикация и снятие выполняются отдельно от сохранения товарной карточки, с предварительным просмотром и подтверждением.
- Одна публичная карточка имеет стабильные `id` и `slug`, явно выбранный источник контента и отдельную подтверждённую привязку товара каждого филиала.
- Филиалы и склады, участвующие в витрине, задаются владельцем в `/owner/storefront`. Браузер клиента не передаёт внутренние `branchId` или `storeId`.
- Наличие считается только по явно разрешённым складам. Используется каноническое поле `LocalStockBalance.available`; резерв повторно не вычитается, дробные количества сохраняются.
- Цена, остаток, адрес, телефон и момент актуальности возвращаются отдельным предложением для каждого публичного филиала. Внутренние закупочные цены, поставщики, движения, резервы и внутренние идентификаторы склада/филиала в DTO отсутствуют.
- Публичные API `/api/public/oils`, `/api/public/oils/[id]`, `/api/public/oils/filters` и совместимые старые `/api/oils*` возвращают только явно опубликованные товары. При проблеме источника отдают ошибку, а не демонстрационные данные.
- VIN-подбор также работает только по опубликованному ассортименту и не может открыть скрытый товар обходным путём.
- В списке товаров CRM добавлены статус и фильтр публикации, в редакторе — блок клиентского сайта, в массовых действиях — «Показать на сайте» и «Скрыть с сайта» с замороженной выборкой и итогом по каждой строке.
- Создание, копирование и импорт не публикуют товар автоматически. Повторная команда идемпотентна. Действия записываются в журнал аудита.
- При нескольких безопасных совпадениях владелец выбирает общую карточку вручную. В список не попадают архивные или несовместимые SKU; backend повторно проверяет доказательство идентичности перед связью.
- Смена CRM-карточки, являющейся источником общих характеристик, вынесена в отдельное подтверждаемое действие и записывается в аудит.

## Безопасное сопоставление

Автоматическая привязка допускается только при доказуемом совпадении: подтверждённая lineage-копия, штрихкод при совпадающем бренде либо точная пара бренд + артикул. Формат продажи, фасовка и технические свойства проверяются отдельно. Наливное и фасованное масло не объединяются. Конфликт или неоднозначность блокируют строку и требуют ручной проверки; эвристическое совпадение по похожему названию не используется.

Скрипт `npm run preview:storefront-oil-matching -- --summary` выполняет только чтение из локально восстановленной актуальной копии Timeweb. Он находит реальные записи «Дачная» и «Гагарина», показывает их ID, активные склады, рекомендуемый основной склад и группы однозначных/неоднозначных/несопоставленных масел. Прямое соединение скрипта с production запрещено защитной проверкой хоста.

## Модель и миграция

Аддитивная миграция находится в `prisma/migrations/20260911150000_storefront_oil_publication/migration.sql`. Она создаёт пустые таблицы конфигурации витрины, публичных карточек, филиальных привязок, аудита и двухфазных пакетных операций. Миграция не содержит backfill и не меняет существующие товары, остатки или цены.

Ключевые файлы реализации:

- `src/lib/storefront-publication.ts`, `src/lib/storefront-product-identity.ts` — права, сопоставление, preview/apply, версии и аудит;
- `src/lib/public-storefront.ts`, `src/lib/public-oil.ts` — серверный tenant-контекст и публичный DTO;
- `src/lib/storefront-configuration.ts`, `src/app/owner/storefront/*` — выбор филиалов и складов владельцем;
- `src/app/inventory/products/ProductsClient.tsx`, `src/lib/catalog-search.ts` — редактор, статусы, фильтры и массовые действия CRM;
- `src/app/api/public/oils/*`, `src/app/api/oils/*`, `src/app/api/storefront/*` — публичные и авторизованные endpoints;
- `scripts/preview-storefront-oil-matching.mjs`, `scripts/test-storefront-publication.mjs` — read-only аудит и локальная приёмка.

## Порядок ввода

1. Получить и проверить резервную копию Timeweb, восстановить её локально.
2. На локальной копии выполнить read-only preview и согласовать реальные филиалы, склады и неоднозначные товарные пары.
3. После отдельного разрешения применить аддитивную миграцию в Timeweb.
4. В CRM под владельцем открыть `/owner/storefront`, включить только «Дачная» и «Гагарина» и явно выбрать допустимые склады.
5. Если в общей БД будет больше одной активной витрины, установить `PUBLIC_STOREFRONT_SLUG`; иначе публичный API намеренно вернёт `503`, чтобы не смешать организации.
6. В каталоге CRM отфильтровать готовые масла, открыть предварительный просмотр массовой публикации, проверить количество строк, филиалы и причины блокировки, затем подтвердить.
7. Проверить публичный список, одну карточку с двумя предложениями, скрытие и повторную публикацию; только после этого переключать клиентский трафик.

До выполнения этих шагов витрина остаётся пустой. Автоматического массового включения старого каталога нет.

## Актуализация и отказоустойчивость

Ответы товарных API помечены `Cache-Control: no-store`, поэтому следующий запрос читает актуальную цену, остаток и статус из CRM. Открытая вкладка каталога обновляет данные раз в 60 секунд и сразу после возвращения вкладки в активное состояние. Это целевой интервал реализации, а не замер production: миграция, настройка, публикация и deploy в этой работе не выполнялись.

При недоступности БД или неполной/неоднозначной настройке API возвращает `503`. Пустой успешный результат остаётся пустым каталогом. Демонстрационный ассортимент и устаревший кэш не подставляются.

## Локальная проверка

- `npm run test:storefront-publication` — правила идентичности, готовность, два филиальных предложения, разные цены, дробные остатки, отсутствие внутренних полей и DML в миграции.
- `npm run test:storefront-publication-db` на одноразовом localhost PostgreSQL — реальные транзакции двух филиалов, создание/повтор публикации, стабильный ID, раздельные цены и дробные остатки, allowlist складов, ноль/нет связи, смена источника, скрытие списка/прямой карточки/фасетов, stale-preview и проверка прав. Скрипт отказывается работать не с localhost или с БД без `storefront_test` в имени.
- `psql ... -f prisma/migrations/20260911150000_storefront_oil_publication/migration.sql` на отдельной минимальной временной БД — успешный `COMMIT` всей additive migration.
- `npx prisma validate` — согласованность схемы.
- `npx tsc --noEmit` — типы.
- `npm run test:branch-isolation` — branch query policy, production guards и изоляция.
- `npm run check:timeweb-only` — guard единственного поддерживаемого production-контура.
- `NODE_OPTIONS=--max-old-space-size=8192 npm run build` — успешная production-сборка и подготовка standalone runtime. При лимите 4 ГБ локальная сборка завершилась OOM, поэтому постоянная конфигурация не менялась.
- Точечный ESLint изменённых TypeScript/TSX-файлов — без ошибок; сохранено одно существующее предупреждение React Hooks в редакторе товаров.

Read-only preview реальных ID пока не выполнен: локальный PostgreSQL из `.env.local` на `127.0.0.1:5432` недоступен. Это намеренно не обходилось подключением к production.

Отдельный исторический реестр `audit:branch-models` уже отстаёт от текущей схемы: генератор останавливается на ранее не классифицированной `SalesAnalyticsMetric`, а сохранённый ожидаемый размер реестра — 145 моделей при 176 в текущей схеме. Новые storefront-модели внесены в правила генератора и рабочий branch-isolation guard, но несвязанный полный пересмотр старого реестра в эту задачу не включался.

В кодовой базе подтверждён существующий consumer `/client-site` через `/api/oils*`; он и новый канонический `/api/public/oils*` обновлены. Фактический внешний production URL и наличие отдельного Tilda-потребителя не проверялись без live-доступа; Tilda, DNS и хостинг не изменялись.

## Действия, требующие отдельного разрешения

- получение/восстановление актуальной копии production, если это меняет внешнее состояние;
- применение миграции;
- первичная настройка филиалов и складов в production;
- массовая публикация существующих масел;
- commit, push и deploy.
