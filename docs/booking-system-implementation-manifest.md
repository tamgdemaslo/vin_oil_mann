# Собственная система записи: implementation manifest

Дата исследования: 16.08.2026.

## Состояние до реализации

1. **Канонической Prisma-модели записи не было.** Рабочий журнал получал записи напрямую из Yclients; локальная публичная демо-форма держала отдельные записи в памяти процесса.
2. **Журнал использовал `/api/yclients`.** Через него загружались конфигурация, сотрудники, услуги и records, а `POST`/`PUT`/`DELETE` создавали, переносили и удаляли записи в Yclients.
3. **Из Yclients приходили** филиальная company-конфигурация, staff, services, даты/времена, records и карточка отдельной записи. Идентификаторы, длительность, клиент, комментарий и источник адаптировались уже в UI журнала.
4. **Локальными были** UI журнала, расчёт координат и длительности блоков, карточка записи, поиск связанных отгрузок, capability-проверки и часть CRM-связей. Сам календарный источник истины локальным не был.
5. **Drag-and-drop** вычислял новое локальное время и колонку мастера в React, затем отправлял `PUT /api/yclients`; после ответа журнал перезагружался.
6. **Клиент** сопоставлялся с `LocalCounterparty` по нормализованному телефону и внешним полям Yclients. Отдельной таблицы клиента записи не существовало.
7. **Автомобиль** хранился в legacy raw-данных контрагента и текстовых snapshot-полях документов; нормализованной коллекции автомобилей одного клиента не было.
8. **История отгрузок** уже искалась по телефону/клиенту через существующие demand/shipment API и отображалась в карточке журнала.
9. **Уведомления** уже работали через `NotificationTemplate`, `NotificationRule`, `NotificationJob`, `NotificationLog` и существующий worker. Создание/перенос/отмена Yclients вызывали этот движок.
10. **Филиал** определялся через активный branch session и `BranchMembership`; интеграционная конфигурация Yclients также была привязана к филиалу.
11. **Сотрудник** определялся через `BranchMembership`, роль и capabilities; Yclients staff id был внешним идентификатором, а не локальным владельцем календарного ресурса.
12. **Переиспользованы** `Branch`, `BranchMembership`, `LocalCounterparty`, нормализация телефона, branch scope/capabilities, audit log, notification engine, история отгрузок и существующий UX журнала.
13. **Реально отсутствовали** локальная запись, каталог услуг, связь мастер–услуга, график филиала, график мастера, исключения, несколько автомобилей клиента, безопасная ссылка управления и централизованный availability engine.
14. **Prisma migration нужна**, потому что подходящего локального аналога `Booking` не было. Новая `Booking` стала общей сущностью для публичной формы, журнала, Messenger и внутренних команд; отдельная `PublicBooking` не создавалась.

## Реализованная архитектура

- `Booking` + `BookingServiceItem` — единственный источник истины для новых и импортированных записей.
- `BookingService`, `BookingMasterService`, недельные графики и исключения — филиальные настройки календаря.
- `ClientVehicle` — CRM-расширение `LocalCounterparty` для нескольких нормализованных автомобилей; отдельной `BookingCustomer` или `BookingVehicle` нет.
- Один серверный availability service используется публичной формой, management link, внутренним журналом, Messenger и существующим ИИ-агентом.
- Создание и перенос сериализуются транзакцией PostgreSQL с advisory lock и повторной проверкой пересечения.
- Существующий журнал сохранён и переключён на локальный adapter `/api/booking-journal`; drag-and-drop продолжает работать с тем же `Booking`.
- Yclients оставлен только read-only источником идемпотентного импорта `LEGACY_YCLIENTS`; новые записи туда не отправляются.

Порядок безопасного production-перехода описан в `docs/booking-system-cutover.md`.
