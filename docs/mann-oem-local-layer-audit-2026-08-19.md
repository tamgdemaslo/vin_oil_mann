# Аудит MANN → OEM Parts → LocalProduct

Дата: 19 августа 2026 года.

Статус: обязательный предварительный аудит завершён. Алгоритм определения автомобиля и frozen Dataset D не изменялись. Товары не объединялись, не удалялись и не архивировались.

## Область и ограничения

Аудит выполнен на сохранённом Dataset D и офлайн-снимке локального каталога от 18 августа 2026 года. Снимок содержит одну ветку каталога: 1 722 товарные карточки, из них 1 571 активная и 151 архивная. Поэтому цифры дублей относятся только к этому снимку одной ветки, а не ко всем веткам production.

В снимке нет позиций документов. Использование карточек в отгрузках, приёмках и иных документах не проверялось и не может быть основанием для автоматического merge. Детализированный машинный результат сохранён в `outputs/mann-matching-private/dataset-d.oem-local-layer-audit.json`.

## 1. Как MANN article сейчас ищется в LocalProduct

`matchMannArticlesToLocalProducts()` работает в контексте одной ветки и объединяет три источника:

1. собственные `article`/`code` карточки с брендом MANN;
2. точный нормализованный токен в `oemParts`;
3. явный `ProductMannLink`.

SQL сначала извлекает кандидатов через compact-поиск по `oem_parts` и `name` и точное compact-сравнение `article`/`code`. Затем `evaluateMannArticleProductMatch()` отбрасывает кандидатов без точного токена. Результаты дедуплицируются по `LocalProduct.id` и уже возвращаются массивом `localMatches`.

Проблема находится после поиска: один сильный результат получает `found`, несколько сильных — `multiple_matches`; downstream-метрика считает успешным только `found`. Поле `bestMatch` также сохраняет ошибочную модель «выбрать один товар». Это и занизило результат Dataset D.

Дополнительный дефект политики: имя товара участвует в strong-match для MANN-карточки. На стадии конкретного MANN article это основание нужно убрать; название допустимо только для отображения, не для технической совместимости.

## 2. Используется ли OEM Parts фактически

Да. Каноническое production-поле — `LocalProduct.oemParts`, физически `oem_parts TEXT`. Это не JSON, не массив и не отдельная relation. Старое `mannName` помечено deprecated; отдельная таблица `ProductMannLink` существует только для явных связей.

В Dataset D именно `oemParts` покрывает 104 из 125 ожидаемых вхождений MANN-референсов. На уровне уникальных референсов — 76 из 95. OEM enrichment из ROSSKO только обновляет `oemParts` существующей карточки и не создаёт товар.

## 3. Реальные форматы OEM Parts

OEM Parts заполнены у 1 098 из 1 571 активной карточки. Получено 43 571 непустых сегментов:

| Формат | Сегментов | Примеры |
|---|---:|---|
| Один compact article/value | 40 117 | `ADB112117`, `CH9496ECO`, `1457429244` |
| Производитель/префикс + article | 3 075 | `FILTRON AP197/5`, `JS Asakashi A9328`, `Mando EAF00308T` |
| Несколько цифровых частей или номеров | 210 | `Mann C 24 054`, `Bosch 1 987 435 097` |
| Смешанное значение с пробелами | 91 | `Hyundai/Kia 28113-F2000`, `Meat&Doria 17455` |
| Текст без цифр | 76 | `HYUNDAI/KIA`, `DENCKERMANN`, `CUK` |
| Разнесённый article | 2 | `W 610/9`, `W 811/80` |

Главный разделитель — `;`: он встречается в 1 076 карточках. Перенос строки есть в четырёх, запятая и `|` в снимке не встречаются. 603 значения заканчиваются `;`. В сегментах есть 3 378 значений с пробелами, 940 с дефисом, 219 с точкой и 148 со слешем.

В проекте сейчас два разных OEM-парсера. На 74 карточках они дают разное число токенов. Это подтверждает необходимость единого parser/normalizer, но не разрешает безусловно удалять все разделители.

## 4. Текущая normalization

`normalizePartArticle()` делает uppercase, Unicode NFKD, удаляет диакритику, унифицирует тире и обратный слеш. Пробелы, точки и дефисы удаляются. Возвращаются два ключа:

- `structural` — сохраняет `/`;
- `compact` — дополнительно удаляет `/`.

OEM parser разбивает строку по переносу, запятой, `;` и `|`, добавляет целый сегмент, отдельные слова и сгруппированные letter+digit части. Бренд MANN централизован только для трёх форм: `MANN`, `MANN FILTER`, `MANNFILTER`.

При этом ROSSKO и общий cross-reference helper используют другие функции нормализации. Требование одной `normalizePartNumberForCrossMatch()` пока не выполнено.

Collision audit показал:

- MANN catalog: 2 064 compact-ключа, одна опасная structural collision — `C27161` и `C2716/1` превращаются в `C27161`;
- собственные article/code: 1 471 ключ, 0 structural collisions и 7 formatting-only variants;
- OEM raw segments: 25 753 ключа, 4 structural collisions и 57 formatting-only variants.

Следствие: compact без слеша нельзя делать безусловным exact identity. Structural-ключ должен оставаться первичным; compact допустим только как контролируемый fallback с дополнительным доказательством.

## 5. Потенциальные duplicate LocalProduct

По минимальному ключу `branch + canonical brand + canonical own article + UOM + package volume + volume + weight` найдены:

- 2 потенциальные группы;
- 5 карточек в этих группах;
- 3 лишние карточки, если группы когда-либо подтвердятся как один SKU;
- одна группа имеет положительный остаток более чем на одной карточке;
- все пять карточек пришли из МойСклад; различия поставщика нет.

Однако собственные brand+article заполнены только у 172 активных карточек, поэтому это не полный аудит всех 1 571 карточек.

Ручная проверка двух групп не подтвердила безопасный merge: в названиях расходятся вязкость и/или объём упаковки, тогда как структурированные SKU-поля заполнены противоречиво. Текущий итог: **2 группы требуют исправления товарных атрибутов, 0 групп подтверждены как безопасные настоящие дубли**. Автоматически объединять их нельзя.

При диагностическом fallback на `code` появляются 3 группы/7 карточек, но там также есть явные различия SKU в названиях. `code` нельзя автоматически приравнивать к собственному артикулу.

## 6. Dataset D: сколько MANN references покрыты через OEM

Оценивались только 52 случая с правильным Top-1 vehicle match. Для всех 52 набор MANN-фильтров совпал с label. Это 125 вхождений и 95 уникальных MANN-референсов.

| Метрика | Вхождения | Уникальные references |
|---|---:|---:|
| Есть минимум один валидный LocalProduct | 104/125 (83,2%) | 76/95 (80,0%) |
| Есть OEM Parts match | 104/125 (83,2%) | 76/95 (80,0%) |
| Есть exact own MANN card | 1 | 1 |
| Есть явный ProductMannLink | 1 | 1 |
| Есть хотя бы один вариант в наличии | 78/125 (62,4%) | 52/95 (54,7%) |

Exact own card и ProductMannLink могут пересекаться с OEM и не прибавляются к coverage повторно.

## 7. Сколько имеют несколько корректных аналогов

- 80 из 125 вхождений (64,0%) имеют несколько валидных LocalProduct;
- 57 из 95 уникальных references (60,0%) имеют несколько валидных аналогов;
- ещё 19 уникальных references имеют ровно один вариант.

Это успех ассортимента, а не ambiguity.

Assortment depth:

- 186 валидных связей product↔reference на 95 уникальных references;
- в среднем 1,96 варианта на reference с учётом нулевого покрытия;
- в среднем 2,45 варианта на покрытый reference;
- медиана — 2, p95 — 5, максимум — 6.

## 8. Сколько реально не покрыты каталогом

Не покрыты 19 из 95 уникальных references (20,0%), или 21 из 125 вхождений (16,8%).

Из 19 уникальных:

- 17 не имеют подтверждающего own MANN/OEM/ProductMannLink evidence;
- 2 имеют только слабое совпадение собственного артикула у другого бренда и остаются `review-only`; технически совместимыми их считать нельзя.

## 9. Обнаруженные false matches

В переоценённой части Dataset D не найдено ни одного strong-result, основанного только на имени или другом неподтверждённом признаке: 0 policy-invalid результатов среди 186 найденных product↔reference связей.

Это не независимая экспертная разметка всех OEM-кроссов, поэтому считать precision окончательно доказанной нельзя. Collision audit обнаружил конкретный safety-risk вне D: `C27161` и `C2716/1` различны в MANN catalog, но совпадают после удаления `/`. Этот кейс должен стать обязательным negative regression test до централизации normalizer.

Substring-предвыборка SQL сама по себе не попала в финальные matches, потому что её фильтрует точное token comparison. Тем не менее `LIMIT 200` и поиск по `name` следует убрать из окончательной архитектуры после утверждения следующего этапа.

## 10. Исправленный end-to-end Dataset D

Старый strict success требовал ровно один LocalProduct. Среди 100 Dataset D это выполнялось только в 4 случаях.

Новый strict success требует правильный Top-1 vehicle, точный MANN filter set и хотя бы один подтверждённый LocalProduct для каждого ожидаемого MANN reference:

- **37/100 = 37,0%** по всему Dataset D;
- **37/52 = 71,2%** среди случаев с правильным Top-1 vehicle;
- прежняя метрика: **4/100 = 4,0%**;
- изменение: **+33 процентных пункта**, без изменения vehicle matcher.

Оставшиеся 15 из 52 правильных vehicle cases провалились только из-за отсутствия локального покрытия минимум одного ожидаемого MANN reference.

## Решение перед реализацией

Числа подтверждают новую бизнес-модель:

- MANN article — reference применяемости;
- один или несколько OEM-подтверждённых LocalProduct — успешный результат;
- настоящие дубли определяются только по товарной идентичности, а не по общему OEM reference;
- текущий `multiple_matches` должен стать `OEM_MULTIPLE_VALID`, а `localMatches` — явным `compatibleProducts[]`;
- vehicle matcher и frozen Dataset D менять не нужно.

Следующий безопасный этап: централизовать structural part-number parsing, убрать имя из product compatibility evidence, сохранить все аналоги, изменить downstream status/E2E и добавить collision/negative tests. Усиление duplicate prevention и merge flow остаются отдельной задачей после полного branch-aware аудита с document usage.
