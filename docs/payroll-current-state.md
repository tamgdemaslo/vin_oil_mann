# Payroll current state

Дата аудита: 2026-06-24. Обновлено после удаления операционных рабочих смен: 2026-08-17.

Цель документа: зафиксировать существующую систему смен, рабочих дней, ставок, сдельных правил, корректировок, начислений и выплат перед объединением в единый раздел `Финансы -> Зарплата`. Документ намеренно описывает, что уже есть и что нужно переиспользовать, чтобы не создать вторую параллельную payroll-систему и не потерять существующие правила.

## Ключевой вывод

В проекте уже есть рабочий каркас зарплаты:

- `src/app/salary/SalaryDashboard.tsx` - основной frontend зарплаты с KPI, вкладками, календарём рабочих дней, ставками, сдельными правилами, drawer сотрудника и историей;
- `src/lib/payroll.ts` - расчёт зарплаты на лету;
- `src/lib/shift-rates.ts` - ставки назначенных смен;
- `src/lib/piecework-rules.ts` - дефолтные и сохранённые правила сдельной оплаты;
- API `payroll`, `working-days`, `shift-rates`, `piecework-rules`, `bonus-penalties`;
- модели `ScheduledWorkingDay`, `ShiftRate`, `PieceworkRule`, `BonusPenalty`, `ChangeLog` и архивная `LegacyWorkShift`.

Рабочая команда даты теперь формируется только из назначенных владельцем смен `ScheduledWorkingDay`. Кассовая смена определяет операционный доступ, но не назначает зарплатную смену.

Текущая реализация после правки:

- `computePayroll()` берёт только проведённые локальные отгрузки (`LocalDemand.applicable = true`);
- для расчёта используются только назначенные владельцем смены;
- услуги начисляются только единственному мастеру рабочей команды дня;
- товары начисляются только единственному администратору рабочей команды дня;
- конфликт нескольких мастеров/администраторов или отсутствие роли не создаёт двойную оплату и возвращается как `unallocatedPiecework`;
- автоматических штрафов за открытие или закрытие личной смены нет.

## Существующие модели

### `LegacyWorkShift`

Файл: `prisma/schema.prisma`.

Таблица: `shifts`.

Назначение: архив исторических записей. Новые записи не создаются, в расчёте зарплаты и в проверке доступа модель не участвует.

Поля:

- `userLogin`;
- `shiftDate`;
- `startedAt`;
- `endedAt`;
- `closeType`;
- `closedByLogin`;
- `latePenaltyCents`;
- `unclosedPenaltyCents`.

Ограничение: `@@unique([userLogin, shiftDate])`.

Операционные API этой модели удалены.

### `ScheduledWorkingDay`

Таблица: `scheduled_working_days`.

Назначение сейчас: вручную назначенный владельцем рабочий день сотрудника.

Поля:

- `userLogin`;
- `date`;
- `createdByLogin`;
- `createdAt`.

Ограничение: `@@unique([userLogin, date])`.

Переиспользовать обязательно: это уже существующая таблица рабочих дней. Её нужно расширять, а не создавать `EmployeeWorkday` с нуля параллельно.

Недостаёт по ТЗ:

- тип дня: полный день, полсмены, почасовая работа, выходной, отпуск, больничный, неявка, стажировка, другое;
- время начала/окончания;
- часы;
- коэффициент;
- комментарий;
- источник: вручную, график, подтверждено сменой, импорт;
- snapshot ставки на день.

### `ShiftRate`

Таблица: `shift_rates`.

Назначение сейчас: индивидуальная ставка сотрудника за смену с датой начала действия.

Поля:

- `userLogin`;
- `amountCents`;
- `effectiveFrom`.

Используется в `getShiftRateCents(userLogin, shiftDate)`: выбирается последняя ставка с `effectiveFrom <= shiftDate`.

Переиспользовать обязательно: уже реализована важная логика действия ставки по дате.

Недостаёт по ТЗ:

- тип оплаты: смена, час, оклад, оклад + смены, только сдельная, комбинированная;
- полсмены;
- ставка в час;
- выходной/праздничный/сверхурочный коэффициенты;
- `effectiveTo`;
- ставки роли и общая ставка по умолчанию;
- архивирование вместо удаления.

### `PieceworkRule`

Таблица: `piecework_rules`.

Назначение сейчас: сохранённые переопределения сдельных правил.

Поля:

- `targetType`: `service` или `product_group`;
- `targetId`;
- `targetName`;
- `role`;
- `mode`: `fixed` или `percent`;
- `fixedCents`;
- `percentBasisPoints`;
- `createdAt`;
- `updatedAt`.

Ограничение: `@@unique([targetType, targetId, role])`.

Важно: в `src/lib/piecework-rules.ts` есть большой список дефолтных правил. `listPieceworkRules()` объединяет дефолтные правила и записи из БД, причём записи из БД перекрывают дефолты. Frontend должен показывать именно этот merged-list, не пустую новую таблицу.

Недостаёт по ТЗ:

- конкретный товар;
- группа услуг;
- категория товара;
- индивидуальные правила сотрудника;
- правила роли и общие правила одновременно с приоритетами;
- база расчёта в явном поле;
- `effectiveFrom/effectiveTo`;
- `priority`;
- `status/archive`;
- флаг `stackable` / "суммировать с другими";
- момент начисления.

### `BonusPenalty`

Таблица: `bonus_penalties`.

Назначение сейчас: бонусы, ручные штрафы и системные штрафы за смены.

Поля:

- `userLogin`;
- `date`;
- `amountCents`;
- `type`: `bonus`, `penalty_late`, `penalty_unclosed`, `penalty_manual`;
- `comment`;
- `createdByLogin`;
- `createdAt`.

Переиспользовать как основу вкладки `Корректировки`.

Недостаёт по ТЗ:

- типы `adjustment`, `deduction`, `recalculation`, `compensation`, `advance`;
- период;
- причина;
- связанный документ;
- вложение;
- статус/отмена.

### `ChangeLog`

Таблица: `change_logs`.

Назначение сейчас: audit log изменений ставок, правил, рабочих дней и корректировок.

Используется:

- `/api/working-days`;
- `/api/shift-rates`;
- `/api/piecework-rules`;
- `/api/bonus-penalties`;
- `/api/payroll/history`.

Нужно расширить перечень сущностей для будущих периодов, выплат и ручного распределения конфликтных начислений.

### `CashShift`

Таблица: `cash_shifts`.

Назначение: кассовая смена, открытие/закрытие кассы, операции и расходы.

Важно: не использовать как рабочий день мастера. Может быть только справочным сигналом в календаре зарплаты.

### `LocalDemand` и `LocalDemandPosition`

Таблицы:

- `local_demands`;
- `local_demand_positions`.

Используются в `src/lib/payroll.ts` как источник отгрузок, услуг и товаров за период.

Есть:

- `LocalDemand.documentDate`;
- `LocalDemand.applicable`;
- `LocalDemand.sumCents`;
- `LocalDemand.positions`;
- `LocalDemandPosition.assortmentType`;
- `LocalDemandPosition.name`;
- `LocalDemandPosition.quantity`;
- `LocalDemandPosition.priceCentsPerUnit`;
- `LocalDemandPosition.discount`;
- `LocalDemandPosition.buyPriceCentsPerUnit`;
- `LocalDemandPosition.raw`.

Сознательно не требуется для базового алгоритма:

- исполнитель услуги на строке;
- продавец товара;
- автор/пользователь, который провёл отгрузку;
- активная login-сессия сотрудника;
- кассовая смена как источник назначения зарплаты.

Может понадобиться позже для расширенного распределения:

- несколько исполнителей и доли;
- ответственный сотрудник по конкретной строке товара;
- payroll status начисления по строке;
- связь начисления с конкретной строкой расчёта.

Связанные данные вроде `DiagnosticMapSession.masterLogin/masterName`, `LocalDemand.createdById/createdByName` и `ShipmentRevision.createdById/createdByName` могут быть справочными сигналами, но не являются источником начисления по текущему ТЗ.

## Существующие API

### `/api/payroll`

GET.

Параметры:

- `dateFrom`;
- `dateTo`;
- `user`.

Назначение: вернуть результат `getCachedPayrollSummary()`.

Ограничения:

- нет периода/snapshot;
- нет статусов периода;
- нет idempotency;
- нет отдельной таблицы расчётов;
- нет отдельного UI-реестра позиций `unallocatedPiecework`, которые требуют распределения;
- расчёт идёт на лету.

### `/api/payroll/history`

GET.

Назначение: история `ChangeLog` по сущностям:

- `piecework_rule`;
- `shift_rate`;
- `scheduled_working_day`;
- `bonus_penalty`.

Ограничения: не включает выплаты, периоды, закрытие периода и отдельные события распределения конфликтных начислений.

### `/api/working-days`

GET: возвращает назначенные смены `ScheduledWorkingDay`.

POST: владелец назначает один день или диапазон.

DELETE `/api/working-days/[id]`: владелец удаляет только назначенный рабочий день.

Плюсы:

- есть единый источник назначений для зарплаты;
- есть audit log.

Ограничения:

- нет bulk endpoint, хотя frontend сейчас делает несколько POST/DELETE;
- нет типов дня, часов, комментария, коэффициента;
- "отсутствие" и комментарии сейчас во frontend локальные, не сохраняются в БД.

### `/api/shift-rates`

GET: владелец получает ставки всех пользователей, сотрудник - свою.

POST: владелец создаёт/обновляет ставку с `effectiveFrom`, есть режим `applyToMonth`.

Плюсы:

- ставка ищется по дате;
- есть audit log;
- можно не переписывать прошлые ставки.

Ограничения:

- только индивидуальная ставка за смену;
- нет `PATCH /:id`, архивирования, типов оплаты, полсмены/часовой ставки.

### `/api/piecework-rules`

GET: владелец получает merged-list дефолтных и сохранённых правил.

POST: владелец создаёт/обновляет правило по `targetType/targetId/role`.

Плюсы:

- существующие дефолтные правила видны как `isDefault`;
- сохранённые правила перекрывают дефолты;
- есть audit log.

Ограничения:

- только `service` для `master` и `product_group` для `admin`;
- нет дат действия;
- нет базы расчёта как хранимого поля;
- нет приоритетов, конфликтов, индивидуальных правил сотрудника;
- нет архивирования.

### `/api/bonus-penalties`

GET/POST/PATCH/DELETE.

Назначение: бонусы и штрафы.

Плюсы:

- уже может стать вкладкой `Корректировки`;
- есть audit log.

Ограничения:

- нет авансов/выплат как отдельной сущности;
- выплаты сейчас определяются через РКО/кассовые расходы.

### Удалённые API личных смен

Маршруты `/api/shifts/*` и задача автозакрытия удалены. Операционный статус дня определяет только `CashShift`.

Фактически главный payroll UI.

Есть:

### `/cabinet/penalties`

Старая страница штрафов/бонусов. По целевой архитектуре должна быть закрыта редиректом или объединена во вкладку `Корректировки`.

## Что есть в БД/коде, но не раскрыто полноценно во frontend

- Дефолтные сдельные правила из `DEFAULT_TARGETS` показываются во вкладке правил, но не имеют дат действия и базы расчёта как редактируемого поля.
- `ChangeLog` есть, но покрывает не все payroll-события.
- `vehicleHistory.unallocatedPiecework` теперь может вернуть позиции, которые не начислены из-за отсутствия роли, конфликта роли или отсутствующего правила.
- `PayrollPeriod`, `PayrollPeriodEmployee` и `PayrollAccrualLine` уже сохраняют закрытый snapshot периода, но reversal ledger и отдельная модель выплат ещё не реализованы.
- `DiagnosticMapSession.masterLogin`, `LocalDemand.createdById/createdByName` и `ShipmentRevision.createdById/createdByName` существуют, но не должны подменять рабочую команду дня.
- `CashExpenseOrder` используется как источник фактических выплат/авансов через эвристику по статье/назначению платежа, но отдельной `PayrollPayment` пока нет.

## Дубли и пересечения

- `CashShift` - единый операционный статус дня филиала.
- `ScheduledWorkingDay` - назначенная владельцем смена для расчёта зарплаты; она не открывает доступ к рабочим разделам.
- `LegacyWorkShift` - только архив старых записей без runtime-использования.
- `BonusPenalty` сейчас одновременно покрывает бонусы, штрафы и ручные корректировки. В целевой схеме её можно расширить или мигрировать в `PayrollAdjustment`, сохранив ID/историю.
- Фактические выплаты сейчас не отдельная payroll-сущность, а вычисляются из `CashExpenseOrder` и попадают в snapshot строками `payout`.

## Что переиспользовать

- `ScheduledWorkingDay` как базу для `EmployeeWorkday`.
- `ShiftRate` как базу для `ShiftRateRule`.
- `PieceworkRule` и `DEFAULT_TARGETS` как источник существующих сдельных правил.
- `BonusPenalty` как базу для вкладки `Корректировки`.
- `ChangeLog` как текущий audit log.
- `computePayroll()` как текущий расчёт с распределением по рабочей команде дня.
- `CashExpenseOrder` как временный источник фактических выплат до введения `PayrollPayment`.

## Нужные миграции

Перед миграцией нужен backup и dry-run отчёт по фактической БД.

Минимальный безопасный путь:

1. Расширить `ScheduledWorkingDay` полями типа дня, часов, коэффициента, комментария и источника. Не удалять старые строки.
2. Расширить `ShiftRate` или добавить совместимую таблицу версий ставок с типом оплаты, полсменой, часовой ставкой, коэффициентами и `effectiveTo`.
3. Расширить `PieceworkRule` датами действия, базой расчёта, приоритетом, статусом, `stackable`, моментом начисления и optional employee scope.
4. Добавить таблицу/представление распределения конфликтов, если нужно вручную назначать доли при нескольких мастерах или администраторах.
5. Доработать `PayrollPeriod`, `PayrollPeriodEmployee`, `PayrollAccrualLine` до полного reversal ledger и добавить `PayrollPayment`.
6. Добавить UI/API для `unallocatedPiecework` и ручного распределения конфликтных начислений.
7. Расширить `ChangeLog` событиями выплат, закрытия периода и ручного распределения начислений.

## Что нельзя делать

- Нельзя удалять `PieceworkRule` или дефолтные правила.
- Нельзя создавать новую пустую таблицу правил вместо `listPieceworkRules()`.
- Нельзя считать `CashShift` рабочим днём мастера.
- Нельзя считать отсутствие входа мастера в аккаунт отсутствием на работе.
- Нельзя начислять услугу или товар всем сотрудникам одной роли; при конфликте начисление должно требовать распределения.
- Нельзя менять прошлые периоды без snapshot/корректировки.

## Ближайшие frontend-правки после аудита

- В меню `Финансы` оставить один пункт `Зарплата`.
- `/finance/shifts` и `/cabinet/shifts` редиректить на `/salary?tab=workdays`.
- В `/salary` поддержать query `tab=workdays`.
- Переименовать вкладку `Ставки` в `Ставки смен`.
- Разделить текущую `Историю выплат` на видимые вкладки/представления `Корректировки`, `Выплаты`, `Периоды` без потери существующих источников данных. Audit log оставить как вторичный `Журнал изменений`.
- В интерфейсе явно разделять кассовую смену филиала и назначенные смены для расчёта зарплаты.
