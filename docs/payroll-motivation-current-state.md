# Payroll motivation current state

Дата аудита: 2026-06-24.

Цель: зафиксировать текущее состояние сотруднической части `Финансы -> Зарплата` перед внедрением интерактивного экрана `Мой заработок`. Важно: мотивационный слой не создаёт вторую payroll-систему и не меняет финансовые правила. Источник истины остаётся существующий `computePayroll()` и текущие модели зарплаты.

## Что уже есть

- Owner-экран зарплаты: `src/app/salary/SalaryDashboard.tsx`.
- Employee-режим: тот же компонент, но `mode = "employee"` и API `/api/payroll` принудительно ограничивает расчёт текущим логином.
- Drawer детализации сотрудника: `SalaryDashboard.tsx`, блок `selectedRow`.
- Группировка начислений по отгрузкам: `vehicleHistory` из `src/lib/payroll.ts`, `pieceworkBreakdownByLogin`.
- API расчёта: `GET /api/payroll`.
- API рабочих дней: `GET/POST /api/working-days`.
- API ставок: `GET/POST /api/shift-rates`.
- API сдельных правил: `GET/POST /api/piecework-rules`.
- API выплат/корректировок: `GET/POST/PATCH/DELETE /api/bonus-penalties`, выплаты временно определяются через РКО.
- Механизм ролей: `src/lib/auth.ts`, роли `owner`, `admin`, `master`.
- Рабочие дни: `ScheduledWorkingDay` плюс фактические `Shift`.
- Правила мастера/администратора: `PieceworkRule` + дефолты из `src/lib/piecework-rules.ts`.
- Возврат отгрузки в черновик: `ShipmentRevision` хранит историю событий, но payroll snapshot/reversal пока не материализован отдельными строками.

## Что доступно сотруднику сейчас

До этой правки сотрудник видел вкладку `Расчёт` как урезанную таблицу по себе и мог раскрыть drawer. Это объясняло итог, но не давало первого экрана с заработком за сегодня, неделю, месяц, лентой начислений и прогрессом.

После первого шага добавлен `GET /api/payroll/self/dashboard` и отдельный UI `Мой заработок` в employee mode:

- KPI: сегодня, текущая смена/день, неделя, месяц, выплачено, к выплате;
- последние начисления по отгрузкам;
- раскрытие отгрузки до позиций;
- безопасное пояснение правила и основы расчёта;
- предварительные суммы отделены от подтверждённых;
- командный прогресс без точных выплат напарников;
- блоки цели, прогноза, качества, возможностей, достижений и признания с честными empty-state.

После второго шага добавлен постоянный мотивационный слой:

- миграция `20260624190000_payroll_motivation`;
- модели Prisma для целей, достижений, признания, командных целей и настроек видимости;
- `src/lib/payroll-motivation.ts` с raw SQL-доступом и fallback на пустые данные до применения миграции;
- API владельца для целей, признания, overview и настроек видимости;
- employee API для личных целей и признания;
- вкладка владельца `Мотивация` в `Финансы -> Зарплата`.

Важно: чтение employee-dashboard остаётся безопасным до применения миграции, но создание целей/похвалы владельцем требует применённой миграции в базе.

## Что считается сервером

- `/api/payroll/self/dashboard` вызывает `getCachedPayrollSummary()` для диапазонов: сегодня, неделя, месяц.
- Данные берутся из существующего алгоритма: проведённые `LocalDemand`, рабочая команда дня, ставки, правила, корректировки и выплаты.
- API отдаёт только начисления текущего сотрудника. Владелец может передать `previewUser`, обычный сотрудник не может запросить чужие данные.
- Командный блок отдаёт агрегаты по отгрузкам/услугам/товарам, но не точные суммы коллег.

## Что пока считается на frontend

- Раскрытие карточек отгрузок.
- Фильтрация списка `Мои отгрузки` по периоду/статусу.
- Визуальный прогресс цели, если API начнёт возвращать реальные цели.

Финансовые KPI и суммы начислений не считаются только в браузере.

## Какие API переиспользуются

- `GET /api/payroll` остаётся API расчётной таблицы владельца.
- `GET /api/payroll/self/dashboard` переиспользует тот же `computePayroll()`.
- `GET /api/working-days` остаётся источником календаря.
- `GET /api/piecework-rules` остаётся источником правил.
- `GET /api/bonus-penalties` и РКО остаются временным источником корректировок и выплат.

## Что перенесено на главную сотрудника

- Итоги за день, неделю и месяц.
- `К выплате` и `Выплачено`.
- Сдельные начисления по отгрузкам.
- Раскрытие позиций внутри отгрузки.
- Статус `Предварительно`, пока нет закрытого payroll-периода в БД.
- Командный прогресс без зарплат коллег.
- Empty-state для цели, достижений и признания.

## Где остаётся дублирование

- Drawer сотрудника у владельца продолжает показывать детализацию сотрудника.
- Employee-dashboard показывает похожую расшифровку, но сразу на главном экране и только по текущему сотруднику.
- После внедрения постоянных `PayrollPeriod/PayrollAccrualLine` стоит вынести форматирование accrual card в общий компонент.

## Подтверждённые и предварительные расчёты

Подтверждено сейчас:

- отгрузка проведена (`LocalDemand.applicable = true`);
- рабочая команда даты определена;
- правило найдено;
- сумма вошла в текущий payroll response.

Предварительно сейчас:

- payroll-период не закрыт в БД;
- нет materialized accrual/reversal строк;
- отгрузка может быть возвращена в черновик;
- правила или рабочие дни могут быть изменены до закрытия периода.

Поэтому employee-dashboard честно показывает текущие суммы как `PRELIMINARY`, а `confirmed.amountCents = 0` до появления серверного закрытия периода.

## Какие события могут отменить или изменить начисление

- Отгрузка возвращена в черновик.
- Отгрузка проведена повторно с другими позициями.
- Изменена рабочая команда дня.
- Появился конфликт нескольких мастеров или администраторов.
- Удалено/изменено сдельное правило.
- Период пересчитан.
- Возврат товара или рекламация.
- Выплата закрыта частично или полностью.

Текущий UI не удаляет silently существующие начисления из карточек вручную, но полноценная история `REVERSED` требует materialized payroll accrual/reversal модели.

## Что теперь материализовано

Добавлены постоянные сущности:

- `PayrollGoal`;
- `PayrollAchievementDefinition`;
- `PayrollAchievementAward`;
- `EmployeeRecognition`;
- `PayrollTeamGoal`;
- `EmployeeMotivationSettings`.

Они не копируют существующий расчёт зарплаты и не создают вторую таблицу финансовых правил. Цели и признание работают как мотивационный слой поверх текущего payroll response.

## Что добавлено для закрытия периода

После третьего шага появился первый серверный snapshot закрытого периода:

- `PayrollPeriod`;
- `PayrollPeriodEmployee`;
- `PayrollAccrualLine`;
- миграция `20260624193000_payroll_period_snapshots`;
- API `GET /api/payroll/periods`;
- API `POST /api/payroll/periods/close`;
- вкладка `Периоды` теперь читает закрытые периоды из БД;
- статус строк расчёта берётся из серверного списка закрытых периодов, а не из `localStorage`;
- employee-dashboard показывает `CONFIRMED`, если текущий месячный период уже закрыт.

Snapshot строится поверх существующего `computePayroll()`, поэтому не создаёт вторую систему расчёта.

## Что всё ещё не материализовано полностью

- полноценный reversal ledger для отменённых начислений после закрытия;
- открытие/разблокировка закрытого периода с отдельным audit flow;
- ручное распределение конфликтных начислений;
- payroll-выплаты как отдельная модель вместо текущей привязки к РКО.

Эти сущности нужны для статусов `REVERSED`, корректного перерасчёта после возврата отгрузки в черновик и юридически более строгой ведомости.
