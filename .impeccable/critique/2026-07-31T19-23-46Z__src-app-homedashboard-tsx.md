# Аудит главной страницы Эко-платформы

Цель: `src/app/page.tsx` → `src/app/HomeDashboard.tsx`; production: `https://www.tamgdemaslocrm.ru`.

## Итог

Главная уже выглядит как предметный операционный центр, а не как шаблонный dashboard: есть смена, касса, записи, клиенты, отгрузки и быстрые действия. Главная проблема — не визуальная, а продуктовая: интерфейс иногда показывает правдоподобные нули и критические статусы вместо честного состояния «данные не загрузились». Для внутренней CRM это подрывает доверие сильнее, чем любой косметический недостаток.

Общая оценка: **20/40**. P0: 0, P1: 3, P2: 5, P3: 2.

## Anti-pattern verdict

Это не generic AI-dashboard: терминология и операции хорошо привязаны к бизнесу. Но заметно итеративное наслоение: три поколения homepage CSS, дублированные responsive-ветки, повторяющиеся KPI и действия, обещание глобального поиска без работающего поиска, legacy-компонент смены внутри новой визуальной системы.

## Что уже хорошо

1. Главная правильно собрана вокруг текущего дня: филиал, дата, смена, касса, записи, клиенты и отгрузки.
2. Рабочие строки сразу дают контекст и действие: клиент, машина, статус, следующий шаг.
3. Палитра спокойная и уместная; статусы дублируются текстом, основные CTA контрастны, предусмотрен `prefers-reduced-motion`, есть отдельная мобильная компоновка.
4. Основные назначения ссылок существуют, таблица помещена в горизонтальный scroll-контейнер, viewport и нижняя mobile-nav настроены здраво.

## Приоритетные проблемы

### P1 — Интерфейс выдаёт сбой API за реальные нули и «касса закрыта»

**Почему важно.** `tryResponseJson` возвращает `null` при HTTP 401/500 или невалидном JSON и не бросает исключение. `HomeDashboard` затем подставляет `?? 0`, а `cashClosed = dashboard?.cash.status !== "open"` становится `true`, когда dashboard отсутствует. Владелец может принять ложное операционное решение.

Дополнительно API выбирает «ближайшую» запись как будущую либо первую запись дня, поэтому прошедшая запись может оказаться подписана как ближайшая. Прогноз 0.45–1.15 выглядит математически точным без объяснения допущений.

**Исправить.** Ввести состояния `loading / success / partial / error / stale`; обязательный operations-запрос проверять через `response.ok`; не создавать кассовые предупреждения из `null`; добавить время обновления, retry и revalidation при возврате вкладки в фокус; прошлую запись не называть ближайшей; раскрыть основание прогноза.

Команда: `$impeccable harden`.

### P1 — Одна и та же главная и финансовый DTO показываются всем ролям

**Почему важно.** Роль в основном влияет на блокировку смены, но owner-финансы, CRM и отгрузки остаются в интерфейсе. Серверный operations route проверяет сессию и филиал, но не формирует role-specific DTO и отдаёт revenue/profit любому авторизованному пользователю. Для мастера это одновременно лишний шум и потенциальная утечка коммерческой информации.

**Исправить.** Формировать DTO на сервере по роли: owner — деньги, прибыль, отклонения; admin — очередь, касса, сообщения; master — смена, назначенные работы, диагностика. Заблокированные действия не должны оставаться видимыми dead ends.

Команда: `$impeccable shape`.

### P1 — Responsive-дубликаты создают неверные якоря и до 9–12 запросов при старте

**Почему важно.** Mobile и desktop DOM монтируются одновременно и только скрываются CSS. Для заблокированного мастера одновременно появляются два stateful `ShiftButton`; каждый сам грузит session/shift/cash, а родитель ещё грузит shift/cash/dashboard. Также дублируется `id="shift-control"`, и desktop-якорь может попасть в скрытый mobile-блок.

**Исправить.** Загружать shift/cash/dashboard один раз и передавать состояние дочернему контролу; не монтировать два stateful responsive-дубликата; сделать один общий shift-control либо уникальные ID.

Команда: `$impeccable optimize`.

### P2 — Очередь внимания не является настоящим приоритетным списком

**Почему важно.** Сигналы добавляются в фиксированном порядке и обрезаются через `.slice(0,6)`; заголовок считает уже обрезанный массив. Критичность, дедлайн и влияние не участвуют в сортировке, а те же данные повторяются в KPI и других карточках.

**Исправить.** Создать единую очередь, сортировать по severity → deadline → business impact, показывать первые 3–4 элемента и честное «Ещё N», убрать дублирующие сигналы из соседних блоков.

Команда: `$impeccable distill`.

### P2 — Поиск в шапке обещает функцию, которой нет

**Почему важно.** Поле `readOnly`, исключено из tab order и скрыто от assistive technology, но визуально предлагает `⌘K`. Пользователь будет пытаться использовать основной accelerator и считать интерфейс сломанным.

**Исправить.** Реализовать command palette/поиск либо убрать поле и shortcut до готовности.

Команда: `$impeccable clarify`.

### P2 — Мобильной странице не хватает доступного H1 и состояния текущей навигации

**Почему важно.** Единственный H1 находится в скрываемой desktop-ветке; mobile-ветка начинается с `strong` и H2. Активная ссылка «Контроль» отмечена только классом, без `aria-current="page"`.

**Исправить.** Добавить компактный mobile H1 и `aria-current="page"` текущему пункту.

Команда: `$impeccable audit`.

### P2 — Асинхронные состояния не объявляются screen reader

**Почему важно.** Loading имеет только `aria-label`, ошибка — обычный div; нет `role="status"`, `aria-live`, `aria-busy` и `role="alert"`. После fetch меняются критичные показатели, но assistive technology об этом не узнаёт.

**Исправить.** Добавить `aria-busy` на обновляемый регион, polite live-region для загрузки/статусов, `role="alert"` для ошибки.

Команда: `$impeccable audit`.

### P2 — Контраст и touch targets местами не проходят базовый уровень

**Почему важно.** `#737373` на `#f4f6f7` даёт 4.37:1, на `#edf1f3` — 4.17:1; `#a3a3a3` на `#edf1f3` — 2.22:1. Это используется в тексте 10–11 px и нулевых KPI. Главная mobile-кнопка имеет `min-height:38px`, ниже рекомендуемых 44px.

**Исправить.** Укрепить muted/faint-токены до ≥4.5:1 для обычного текста, увеличить главный mobile CTA минимум до 44px, проверить небольшие desktop actions.

Команда: `$impeccable audit`.

### P3 — Глобальный CSS накопил три поколения dashboard-стилей

**Почему важно.** `globals.css` содержит около 58 984 строк и 1.26 MB исходного CSS; homepage-стили идут тремя слоями (`Operations dashboard v3`, `day center layout`, `command-center refresh`). Одни селекторы переопределяются несколько раз, повышая риск каскадных регрессий.

**Исправить.** Свести актуальные стили главной в один слой/модуль, удалить недостижимые правила после visual regression QA, закрепить токены и primitives.

Команда: `$impeccable optimize`.

### P3 — Таблица отгрузок не имеет программного имени

**Почему важно.** У таблицы есть визуальный заголовок карточки, но нет `caption` или `aria-labelledby`.

**Исправить.** Связать таблицу с заголовком через `caption` или `aria-labelledby`; добавить `scope="col"` заголовкам.

Команда: `$impeccable audit`.

## Persona red flags

- **Владелец:** ложные нули и закрытая касса опаснее всего; нет времени последнего обновления.
- **Администратор в пиковый час:** очередь полезна, но не отсортирована по последствиям, часть задач бесшумно скрывается.
- **Мастер с телефона:** ожидает смену и назначенные работы, а видит финансы/CRM/отгрузки; основное действие маловато для быстрого нажатия.
- **Пользователь с assistive technology:** mobile H1 отсутствует, динамические состояния не озвучиваются, часть вспомогательного текста имеет низкий контраст.

## Эмоциональная дуга

Начало удачное: филиал, день и смена быстро ориентируют. Пик — «Требует решения» и рабочие строки. Провал — красная «касса закрыта» или нули, которые могут быть результатом ошибки загрузки. Нижняя часть повторяет уже известные сигналы. Пустые состояния спокойные, но им не хватает времени обновления, retry и признака частичных данных.
